# 核心元对象层

核心元对象层位于各领域元模型之上，是全平台统一的业务锚点。Schema `1.1.0` 当前定义五个核心元对象：人员、原材料、产品、设备、门店。

| 元对象 | 业务职责 | 权威来源 |
| --- | --- | --- |
| 人员 | 责任、权限、审批、操作、技能 | OA / 账号中心 |
| 原材料 | 采购、批次、检验、库存、配方消耗 | ERP / SRM / LIMS / WMS |
| 产品 | 研发、生产、放行、销售、投诉 | PLM / MES / LIMS / ERP / QMS / OMS |
| 设备 | 工艺、产能、维护、校准、异常 | MES / EAM / IoT |
| 门店 | 门店组织、区域、营业状态、库存、订单、履约、客诉、店内设备 | MDM / OMS / POS / ERP |

## 流程约束

每项业务流程必须关联至少一名人员，并关联与业务目的直接相关的原材料、产品、设备或门店。缺少必填核心元对象时，平台只能保存草稿；智脑不可发起执行、提交审批或写入业务系统。

- 原材料采购：人员 + 原材料；可关联产品需求。
- 产品生产：人员 + 原材料 + 产品 + 设备。
- 质量检验与放行：人员必填；原材料、产品、设备、门店按检验或异常对象关联。
- 设备维护与校准：人员 + 设备；可关联受影响产品。
- 市场反馈与投诉：人员 + 产品；线下来源关联门店。
- 门店运营：人员 + 门店；可关联产品和店内设备。
- 门店补货：人员 + 门店 + 产品。

门店稳定标识使用 `Store.store_id`。权威状态、所属组织和经营范围只能来自 MDM/OMS/POS/ERP 投影；客户端声明的门店 ID、来源和状态不能作为授权依据。当前 Demo 提供 `STORE-SH-001`、`STORE-HZ-002` 两个权威对象，并把 `organizationId` 写入可信绑定。停业、整改或超出当前组织数据范围的门店，生产实现必须阻断补货、销售和处置动作。

OA 元模型承担人员对象的身份、组织、角色、审批与审计语义；原材料、产品、设备、门店元模型分别承接供应链、生产质量、设备运维和终端零售语义。

## 与语义上下文服务的关系

五个核心元对象同时是语义上下文图的一级锚点。已授权的源系统事实必须至少关联一个核心元对象，才可进入图谱、被智脑引用或参与影响分析；关系边应保留来源系统、来源记录 ID、业务生效时间、入库时间、组织归属和数据分级。

语义上下文服务负责保存“事实为何可信”的来源与时间语义，并按已计算的角色范围返回证据。账号中心与权限中心仍然负责“谁能看、谁能做”，密钥中心仍然负责“以何种短时租约调用外部系统”。因此，元对象、语义、权限和密钥是协作关系，不可相互替代。

## 运维建模入口

运维人员可在独立语义运营端的“模型校对”中，将 Semantica 从当前演练图抽取的候选对象绑定到以上核心元对象，并编辑字段、来源、主键、分级与关系。候选仅提供结构与证据；对象的核心锚点、来源系统和数据分级未确认前不能通过发布校验。管理 Web 也有独立语义模块，不再把语义层仅作为配置与治理的子项。详见 [SEMANTIC_MODEL_AUTHORING.md](SEMANTIC_MODEL_AUTHORING.md)。

## 兼容与迁移

- `Store` 是新增对象类型；`Person`、`RawMaterial`、`Product`、`Equipment` 的编码和含义不变。
- `/api/meta-objects` 从 `1.0.0` 升级为 `1.1.0`，客户端必须按对象数组动态渲染，不能假设固定四项。
- OMS 模拟数据仍保持约 100 条总记录，新增 `StoreStatusChanged`，订单和履约记录增加 `storeId`。
- 生产迁移需先完成门店主数据去重、组织映射和状态枚举对齐，再建立 `store_id + tenant_id` 唯一约束与组织查询索引。
