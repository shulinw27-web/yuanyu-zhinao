# 语义层元模型与元对象建设说明

## 2026-09-12 来源事实与解释分层

已发布读计划的解释路径分为四层：授权读取/确定性计算 → 本轮引用目录 → 模型选择引用并提出待验证解释 → 服务端校验、填值及输出。`ontology-analysis-claims` 为记录、指标、数据集和已确认空值建立 `r/m/d/g` 引用，绑定快照与根对象；模型不能自填来源字段值、替换计算值或将 0/false 宣称为空。最后仍进行模型版本和权限复验。

解释网关使用原生对象 `answer`，避免合法外层中嵌入损坏 JSON 字符串；内部对象 Schema 不改变普通对话协议。方舟沿用 JSON-object 模式加显式 Schema 指令，所有对象字段、引用与上限仍须服务端实测校验，不能假设供应商已经完成这些业务检查。

这层契约只约束已发布模型的业务消费，不代替元域智营端的人工审阅、案例回放或发布门禁；不新增连接器和数据授权。自由文本只能作为待验证解释/建议，引用存在不等于因果成立；既有财务矛盾检查仍作补充。失败时保留可信计算而抑制解释，不回退展示未经核验的模型原文。接口和验收边界见 [发布消费指南](../guides/PUBLISHED_MODEL_WORKBENCH.md)。

2026-09-10：读计划增加有界谱系展开、状态过滤和声明覆盖范围；人工校对面板展示这些设置。确定性计算与模型解释分离，解释失败不再标记全任务完成。配置形式、上限和安全边界以 [发布消费指南](../guides/PUBLISHED_MODEL_WORKBENCH.md) 为准。

## 2026-09-10 两端消费链路修复

原始失败保留在 [修复前联测](../development/SEMANTIC_WORKBENCH_LOOP_EVALUATION.md)。现已增加 `published-ontology-agent-service` 加载租户匹配的发布定义，`ontology-read-plan-service` 校验并执行有界只读表达式，连接器按 `ontology-query.v1` 逐跳检索并验证完整覆盖。发布前必须使用同一执行器完成正反例回放，指纹变更即失效。模型负责意图和解释，服务端负责权限、外键、去重及算术；查询完成再次检查发布版本和访问范围。见 [契约与操作指南](../guides/PUBLISHED_MODEL_WORKBENCH.md) 及 [修复证据](../development/SEMANTIC_WORKBENCH_LOOP_REPAIR.md)。不能用重新上传业务材料替代发布消费；自然语言需求尚需人工编制和审阅执行方案。

## 2026-09-10 材料工作区与语义保真

扫描/脱敏后的完整文本由 `semantic-material-workspace-service` 经现有治理存储保存，任务仅持有内部引用；按主体与原角色重新校验访问。结构解析独立于模型摘要预算，合并同任务全部材料并报告同名契约冲突。`semantic-world-model-service` 编译不可执行的需求候选，并在 Critic 核对来源/粒度/主键/显式关系覆盖；`semantic-uploaded-sample-service` 在创建、修订、采纳时校验授权上传样本。公共返回不暴露材料引用或完整文本，业务验收与结构校验分别展示。详细上限与生命周期见 [指南](../guides/SEMANTIC_MATERIAL_WORKSPACE.md)，证据见 [回归报告](../development/SEMANTIC_MANUFACTURING_REPAIR.md)。

## 2026-09-09 场景建模增量

通用业务场景与 OA 审批模板分离：通用场景至少一个对象，不要求六条关系或 OA 审批对象；所有模式继续经过平台权限和结构治理。新增 `modelingProfile`、`scenario`、对象 `granularity` 以及关系证据/有效期元数据。场景中的判断与动作采用服务端允许列表和精确版本声明，不执行用户上传代码或模型生成表达式。

发布保存定义快照与指纹，未发布编辑不改变已发布判断版本关联。状态机、事件、字段映射及受限参数纳入指纹；模型变更清除旧构建结果。质量判断支持直接字段适配与等级/新鲜度参数，已接入既有非定向质量分析，其他入口和任意工具自动生成不在本次实现内。

`decision-binding-service` 对有身份范围的记录执行只读判断；样本回放比较草稿与已发布定义。`ontology_case_replay` 仅按租户/主体保存结果与版本引用，不保存原始样本。可选发布门禁绑定发布主体与精确指纹。

`ontology-runtime-service` 统一人工与 Agent 发布入口。`ontology_publication` 持久化发布操作版本和指纹，短期并发拒绝、超时保留待对账状态。只有独立服务回执的版本/指纹匹配且本地草稿未变，才提交平台发布状态。响应不确定后重试只读查询，不自动重新发布。这是保守的跨服务协调基线，不是分布式事务或外部自动补偿。依赖分析仍只覆盖模型内声明。

Semantica 边界同步允许独立对象类型、保留粒度和场景元数据。语义服务不承担 IAM、业务执行或任意规则计算。界面明确区分本地合成演练和独立服务校验。详细字段与用法见 [业务场景建模指南](../guides/ONTOLOGY_SCENARIO_MODELING.md)，证据见 [验收记录](../development/ONTOLOGY_MODELING_ACCEPTANCE.md)。以下原有建设说明应结合本节的新实现边界理解。

## 建设结论

身份映射追加：`ontology-identity-service` 在回放入口核验显式 source→canonical 对照，来源身份按系统/类型/编号隔离，统一身份按对象类型/统一编号比较；不使用名称、相似度、隐式大小写转换或前导零消除。模型类型与粒度、来源系统、组织范围、双时间及确认性质共同约束。一个来源多重映射或竞争修订返回冲突，重分配不能覆盖原断言。服务只产生报告，不向企业主数据、历史事实、IAM 或独立 Semantica 图写入映射。

同日追加：`temporal-relation-service` 提供有界实例关系查询，复用 `case-replay` 的认证、模型指纹、版本比较和报告隔离。`at` 是业务有效时间，`knownAt` 限定可见修订；按来源系统/关系编号聚合完整修订，再计算有效期、撤回与基数冲突。端点和全部修订先过范围准入，拒绝悬空端点、错来源、重复版本及身份变更。推断不作为权威事实，样本缺失不当作全域不存在。未新增事实写接口，未部署时态数据库，也未改写独立 Semantica 事实图。

当前语义层已形成三层结构：核心元对象层负责统一业务锚点；业务元模型层定义对象、字段、关系、状态和控制规则；Semantica 上下文图承载已经授权的事实、来源和影响关系。推荐从独立元域智营 Agent 的任务工作台生成候选，再进入“模型校对”维护草稿；管理 Web 的语义层也是独立模块，不再只归入配置与治理。平台将通过校验的定义用于语义映射和工作流控制，运营人员不需要直接编辑图数据库。具体交互见 [元域智营指南](../guides/元域智营-Agent操作指南-v1.0.md)。

## 建模范围：选系统是必选项（2026-09-25）

在元域智营端 Agent 工作台发起**建模**或**来源预检**时，必须先**显式选择来源系统**。范围只有两个入口：运营人员在「建模来源范围」面板里的勾选，或调用方显式声明「全部已登记系统」（只读巡检、来源清单预览）。**没有「推断为空就回落到全部可访问连接器」这回事**——历史实现让「文本里碰巧出现系统名」和「什么都没提到」分别产生两种不同的隐式范围，界面上都看不出来，已删除。

- **四类拒绝**：未选择（400 `SEMANTIC_SYSTEM_SCOPE_REQUIRED`）、编码不在注册表（400 `SEMANTIC_SYSTEM_UNKNOWN`）、在注册表但无受控连接器（400 `SEMANTIC_SYSTEM_NOT_REGISTERED`）、超出角色数据域（403 `SEMANTIC_SYSTEM_SCOPE_FORBIDDEN`）。
- **勾选不是提权**：面板的勾选只决定本次分析范围，不改变数据授权（[ADR-001](adr/ADR-001-semantic-permission-separation.md)）。但若所选系统超出角色数据域，任务会被**阻断**而不是静默裁剪到可见子集——否则运营人员会以为范围已经生效，而实际只覆盖了一部分。
- **范围是过滤器，但过滤绝不静默**（2026-09-25 更新）：来源**全部**在所选范围外的对象与随端点悬空的关系**不会进入提案**，但必须以可读清单列出（`excludedObjects` / `excludedRelationships`）并提示「补选对应系统后重跑」。来源**部分**超出范围的对象**保留**并记入 `partialScopeObjects`；来源为 `UNASSIGNED` 的对象**一律保留**。若识别到的对象**全部**被范围排除，任务以独立错误码 `SEMANTIC_PROPOSAL_SCOPE_EXCLUDED_ALL` 拒绝并点名对象与其来源系统——这与「材料里什么对象都没识别到」（`SEMANTIC_PROPOSAL_NO_GROUNDED_OBJECTS`）是两个不同问题，混用会让运营去改材料而不是补选系统。见 [ADR-013](adr/ADR-013-scope-as-filter-with-explicit-exclusions.md)。
- **覆盖结果如实上报**：提案生成后，任务上会记录 `systemScope`：`covered`（有对象标注该系统）、`uncovered`（选了但一个对象都没有）、`excludedObjects`（因来源全在范围外被排除）、`excludedRelationships`（随端点被排除的关系）、`partialScopeObjects`（部分来源超出范围、仍在提案里）、`unassignedObjects`（材料未声明来源、无法追溯）、`mentionedNotSelected`（文本提到但未选择）。界面逐项展示，**不静默丢弃**。
- **范围不继承**：承接口语（`parentTaskId`）时必须重新给出范围；服务端只在拒绝信息里提示上文范围，不会自动沿用。

### 跨系统标识对应与冲突（2026-09-25）

范围内每条系统声明（提案候选对象自带、系统配置映射已声明的对象与字段，或**归属由材料推断且该候选系统在范围内**的抽取对象）会被收拢成**字段目录**，并据此做三件事：

- **标识三档识别**：主键 → 业务键 → **未识别**（记入 `keyGaps` 并给出候选，**不判定**）。判定顺序是「受控词汇表登记的主键 → 由对象名派生的 `<object>_id` → 声明中唯一**指向该对象自身概念**的标识字段」。最后一条是关键：概念不同的标识字段一定是**引用**（外键），不是这个对象自己的标识——否则 `ERP.Inventory` 的 `lot_no`（指向物料批次）会被当成库存自己的标识，凭空成为「物料批次」概念的对齐目标。
- **跨系统对应**：A 的标识字段指向概念 C、B 的标识也指向 C，且两者来自不同系统 → 一条带方向、基数（`n:1`）与逐字证据（`WMS.InboundReceipt.purchase_order_id → ERP.PurchaseOrder.purchase_order_id`）的链接。**定级是三态**（2026-09-25，阶段 4d）：`linkable`（两端形状都已知且一致）／`requires_mapping`（都已知且不同，代理键 ↔ 业务键）／`shape_unknown`（**至少一端形状未判定**——裸名如 `sku` / `product` 在标识白名单里，但没有 `_id` / `_no` / `_code` 后缀，命名规则判不出形状）。**「未知」不得当成「不同」**：把未知并入不同，就会要求人为一件机器尚未判明的事写映射依据，说明文案还会写成「两端键形状不同（null / agent）」——读不通。
- **四类冲突显式上报**：`ambiguous_identifier`（泛化标识，归属不明，且**不参与**链接推导）、`alias_divergence`（同一概念多个字段名）、`key_shape_incompatible`（同一概念上代理键与业务键混用）、`declaration_divergence`（同一对象名/同一张表在两处声明中字段集不一致）。**同名不等于同一实体**，一律上报，禁止静默合并。

**这些对应关系是假设，不是证据**：它们由字段名归一化加一张人工登记的**事务概念别名表**推出，因此**不自动并入** `relationshipTypes`。草稿里的关系仍只容纳受控词汇表登记的关系与材料中带逐字证据的外键。

**确认后才生效，且生效了也仍看得出是推断**：运营在「跨系统标识对应复核」面板逐条勾选，经既有复核动作（`PATCH .../proposal` 的 `identityLinkConfirmations`）提交。并入的边标 `provenanceType: 'inferred'` 并记录 `derivedFrom`（来源链接 key），因此与材料里逐字写明的边（`declared`）在同一份草稿里**可区分**——这是 [ADR-014](adr/ADR-014-identity-linking-as-assumption.md) 退出条件 1 的要求，决策见 [ADR-015](adr/ADR-015-identity-link-confirmation.md)。四条配套规则：

- **先判资格，再问三态**（2026-09-25，阶段 4e）：一条对应**能不能**并入草稿，判据只有一个——**两端 `objectId` 都在本次候选对象内**（`eligible`，由推导层从草案的 `objectTypes` 构造，与服务端草案校验**读同一个数组**）。不可确认的对应**仍然列出**（它是系统声明里真实存在的跨系统引用）但**没有确认入口**，并带可行动的原因（点名缺哪个对象、它的依据为何、先让它成为候选对象）。确认请求给**专用错误码** `SEMANTIC_IDENTITY_CONFIRMATION_ENDPOINT_OUT_OF_SCOPE`；检查次序固定 **链接存在 → 资格 → 形状 → 映射**。**两个判据不许合并**：链接上的 `declarationSourced` 只回答「依据来自系统配置声明还是本次候选对象」，与资格无关——把两者合成一个 flag 会让界面对一条**实测可确认**的对应宣称「来源系统未进入候选对象」（阶段 4e 修掉的正是这句）。决策见 [ADR-020](adr/ADR-020-identity-link-confirmation-eligibility.md)。
- **确认要问清三件事，按三态各一种输入**（2026-09-25，阶段 4d）：`linkable` 直接确认；`requires_mapping` **必须随确认给出结构化映射定义** `keyMapping`（`fromField` / `toField` 须与链接**逐字一致**、`basis` 四类枚举、`master_data_lookup` 时必填 `lookupSource`、`owner`、`version`），只给自由文本一律拒绝——自由文本回答不了「这条边是否需要经映射、谁维护、哪一版」，而这三件事正是下游必须能机器读到的东西；`shape_unknown` **必须先做形状判定**（`agent` / `business`），判定后**重新定级**该条边（与另一端一致 → 可按值对齐；不同 → 需映射，这时才要映射定义）。**判定不写回字段声明**：`shape` 是**这条边上的结论**，写回会污染字段目录（一处判定影响所有读该字段的地方），代价是同一裸名出现在多条边上要重复判定（实测无此情形）。**结构化映射进草稿**（关系上的 `keyMapping`），但**证据等级不变**（仍 `inferred`——映射是人给的，不是材料写明的外键）。**不做独立映射表实体**：实测 7 条映射无一条被两条边共享，无复用证据，`owner` / `version` 是将来升格的钩子，决策见 [ADR-019](adr/ADR-019-structured-key-mapping.md)。
- **确认集合是全量语义**：省略＝本次不调整；空数组＝撤销全部。服务端每次从确认集合**重建**这类边，客户端自带 `derivedFrom` 的关系一律剔除——确认关口不能靠构造请求绕过。**显式**重新提交一条已不可确认的 key 是 400（客户端拿的是过期结论）；**继承**的确认若变成本次不可并入，不阻断修订，列入 `identityLinkConfirmationReport.droppedStale`。
- **确认项失效必须显式**：显式重新提交一个已不存在的 key 是 400；继承的历史确认因字段修订失效时，不阻断修订但会列入报告与任务回应（`droppedStale`）。形状判定与映射定义同属确认项，随确认撤销一起消失。

**支撑这些对应的等价假设必须先裁定**（2026-09-25，阶段 4c）：`alias_divergence` 的说明里写着「跨系统对接前必须确认它们指向同一个实体」，但此前没有这个入口。实测 11 条对应里有 **9 条**站在这个从未被回答过的前提上——`MaterialBatch` 一个概念下的三个字段名（`lot_no` / `material_batch_id` / `material_batch_no`）就支撑了 4 条。运营在「标识等价假设裁定」面板逐概念回答，经同一复核动作（`PATCH .../proposal` 的 `identityConflictRulings`）提交，决策见 [ADR-016](adr/ADR-016-identity-conflict-rulings.md)：

- **两类裁定**：`same_entity`（确认同一实体，冲突标注已裁定）／`distinct_entity`（确认不同实体，必须给出该概念下字段名的**等价类划分**，且必须是严格划分——至少两组、不重复、不遗漏、不含陌生字段，否则 400）。
- **裁定不写草稿关系**：它改变的是「哪些对应成立」，不产生任何 `provenanceType`——因此与 4b 的 `inferred` 不在同一层，不可能混用。裁定为不同实体时，跨等价类的对应被**撤下**（`withdrawnLinks`）而不是保留为可疑项，它们不再出现在可确认清单里。
- **裁定集合是全量语义**（省略＝不调整、空数组＝撤销全部），与确认集合同构；服务端同样从集合重建，客户端不能靠构造请求绕过。
- **被撤下的对应若此前已被确认**，确认随之失效并写入 `droppedStale`，且原因必须可读地区分「裁定撤下」与「字段修订」——两者要运营做的事完全不同。

**同一对象的同名声明也必须裁定「合并 / 区分粒度」**（2026-09-25，阶段 4c 第三段）：同一系统内同一 `objectId` 的多处声明（受控词汇表、已配置映射、材料抽取）字段集不一致时，目录**默认取字段并集**。这个默认动作此前完全不可见，且并集还会参与标识识别——实测 `MES.ProductionBatch` 的并集条目被判定的标识是 `production_batch_id`，而 MES 的**已配置映射**只声明 `batch_no`。于是标识被记在了一个**没有任何一处声明过的复合体**名下。运营在「同名声明合并 / 区分裁定」面板逐分歧项回答，经同一复核动作（`PATCH .../proposal` 的 `declarationRulings`）提交，决策见 [ADR-018](adr/ADR-018-declaration-divergence-merging.md)：

- **键是分歧项、不是概念**：`object:Inventory`（同名对象被不同系统声明）/ `source:ProductionBatch@mes.production_batch`（同一张表被两处声明）。它与等价裁定的**概念级**键是两套粒度，各自独立校验。
- **两类裁定**：`merge`（确认同一对象，并集从默认动作变成结论）／`distinct`（确认不同对象，须给出这些**声明**的严格划分，每组给出对象名或 `drop` 显式排除，至少保留一组）。
- **`distinct` 的效果是「不并集」**：各组按自己声明的字段识别标识，虚假的并集标识随之消失；裁定同样**不写草稿、不产生证据等级**（改的是字段目录的组成，不是草稿关系）。
- **未裁定也必须披露并集**：条目带 `declarations`（逐处声明与字段）、`exclusiveFields`（只被一处声明列出的字段）与 `declarationState`，`identifierBasis` 要写明「这是在并集上识别的」。披露不等于修正——未裁定仍是并集，`merged_unruled_objects` 与 `unresolvedDeclarationItems` 就是这项的规模口径。
- **撤销必须双向完全回退**：拆分出的对象消失、原条目恢复并集（字段与出处一起回来）。因改名而消失的对应连同其上的确认一并失效，原因写入 `declarationReport.droppedLinks`。
- **顺序是先裁定、后确认**：未裁定的等价前提会以 `unresolvedConcepts` 与「N 条对应尚未裁定」的形式显式出现，界面不会让人在没看过前提的情况下逐条确认。

**材料归属由模型取证、服务端判定，且只是候选**（2026-09-25，阶段 4c 第二段）：这条路此前是断的——模型输出的表名/字段/主键/外键证据都能通过逐字校验，唯独没有「这张表属于哪一处」，于是抽取出的对象一律 `UNASSIGNED`，既进不了字段目录（跨系统对应恒为 0 条），也让 Critic 的「受控来源系统」失败、草稿无法采纳。而现在：

- **模型只给归属原文**（`systemEvidence`，必须逐字来自材料），**契约里没有系统码字段**——让模型直接输出 `ERP` 就是给它一个无法复核的断言入口。系统码由服务端判定，判定只用**系统码与系统名**，**不认业务词别名**（别名表里 ERP 含「采购」「库存」，用于「文本提到什么系统」尚可，用于归属会把「采购订单表」判成 ERP 所有权）。
- **判定结果一律是候选**（`candidateSourceSystems` + 依据），`sourceSystems` 仍是 `UNASSIGNED`。**候选不参与范围裁剪**（模型引用一句归属于范围外的原文，不能因此把对象删掉），但**可以进字段目录**（否则非结构化材料路径的跨系统对应永远是 0 条）；候选在范围内/外都只上报（`candidateScopeObjects`）。
- **零 / 多 / 识别不到三类分别上报，一律不猜**（`attribution.attributed / ambiguous / unattributed`）。
- **候选转事实要走人工确认**（`sourceAssignments`，复用同一复核动作）：依据不得为空，目标系统必须已在注册表；确认后才写入 `sourceSystems`，并**这时才**按范围重新裁剪（对象可能因此被排除，引用它的关系随之排除）。集合是全量语义（省略＝不调整、空数组＝撤销全部并**恢复**被裁掉的对象）。
- 提案上的四类人工结论有**顺序依赖**：先归属确认（对象属于谁）→ 再等价裁定（等价假设成不成立）→ 再同名声明裁定（两处声明是不是同一个对象）→ 最后对应确认（哪些对应进草稿，以及形状判定与映射定义）。顺序不能倒：每一关都在改下一关的**输入**（归属决定字段目录、裁定决定哪些对应存在、声明裁定决定目录的组成）。

算法边界：**范围过滤不改对象抽取算法本身**；标识识别、跨系统对应、「确认后并入」、「等价假设裁定」、「材料归属取证」、「同名声明合并 / 区分裁定」、「标识映射结构化 + 形状判定」与「可确认资格判定」都已落地（确定性，不依赖模型）；**模型只被要求给逐字原文，所有判定都在服务端做**——对象本身仍由模型抽取（`validateNaturalSchema` 的逐字证据要求，缺证据即整表拒绝），该契约在真实模型下的稳定性已单独测量（4 变体 × 3 轮，[ADR-017](adr/ADR-017-model-extraction-attribution.md) 复审条件 4 未触发），但**真实企业材料下的质量未测量**。**四类冲突的处置入口已全部落地**（`alias_divergence` 等价裁定 / `declaration_divergence` 合并·区分粒度 / `key_shape_incompatible` 结构化标识映射 + `shape_unknown` 独立成态），**唯余 `ambiguous_identifier` 的归属指派仍只上报**（实测当前 **0 条**，且粒度须按「系统.对象.字段」而非按概念或对象，无用例驱动）。**未裁定的同名声明分歧仍是字段并集**（披露不等于修正）。**确认这一关的前置条件已唯一化**（2026-09-25，阶段 4e）：可确认 ⟺ 两端对象都在本次候选对象内，判据与服务端草案校验**同源**；不可确认的对应仍列出但无确认入口，带可行动原因（实测 11 条里 **7 可确认 / 4 不可**，不可的四个来源对象只在系统配置声明里存在）。**已知边界**：不可确认的对应会长期存在（只要配置声明里有候选之外的对象），这是如实披露的代价；资格检查排在形状之前，使**形状分支在现有合成数据下于任务级不可达**（两条 `shape_unknown` 的源对象都不在候选内），形状的三条拒绝路径改在纯函数层取证。**候选对象的「来源」与「没被生成」的原因也已可读**（2026-09-26，阶段 4f）：受控目录命中会披露**命中词与覆盖率**（命中 M / 共 12 类）并说明它只是**词面匹配的兜底**（「材料里写到、但目录未覆盖的业务对象不会出现在候选里」）；自然语言抽取的**跳过**给出可区分的原因（`mock_runtime` 模拟运行时 / `not_dictionary_like` 材料缺字典线索），不再静默返回 `null`。**边界如实**：这是**覆盖率级**披露而非**清单级**——能说「可能漏」，不能说「漏了哪个」（点名需要对象抽取能力本身）；`'订单'` 命中 `PurchaseOrder` 是已知过泛词，属受控词表的质量问题。决策理由与复审条件见 [ADR-012](adr/ADR-012-explicit-modeling-scope.md)、[ADR-013](adr/ADR-013-scope-as-filter-with-explicit-exclusions.md)、[ADR-014](adr/ADR-014-identity-linking-as-assumption.md)、[ADR-015](adr/ADR-015-identity-link-confirmation.md)、[ADR-016](adr/ADR-016-identity-conflict-rulings.md)、[ADR-017](adr/ADR-017-model-extraction-attribution.md)、[ADR-018](adr/ADR-018-declaration-divergence-merging.md)、[ADR-019](adr/ADR-019-structured-key-mapping.md)、[ADR-020](adr/ADR-020-identity-link-confirmation-eligibility.md) 与 [ADR-021](adr/ADR-021-candidate-provenance-disclosure.md)。

## 可视化建模流程

1. 启动一个 Mock 场景，使合成事实进入 Semantica 图。
2. 打开业务建模工作台。顶部“语义候选对象库”会显示已观察到的对象类型、字段结构、来源系统和关系证据；未观察到的对象会标为“平台语义契约模板”。
3. 将候选对象加入画布，选择节点后编辑业务名称、语义类型、核心元对象锚点、来源、稳定主键、数据分级、字段和说明。
4. 从关系编辑器新增关系，或采纳 Semantica 给出的“共享业务标识关联”建议。关系画布会实时显示对象和连线。
5. 保存草稿并执行校验。校验通过后才可模拟构建；管理角色可发布版本。

发布操作会先把模型定义送到本机 Semantica 执行二次校验并登记，再完成平台版本发布。若 Semantica 服务不可用、对象主键不在字段中、核心锚点不合法、来源仍为“待观察”或关系引用不存在，发布会被阻止。

## 元对象最小规范

每个可发布对象必须具备以下内容：

| 项目 | 作用 |
| --- | --- |
| 稳定对象编码 | 语义类型的长期标识，发布后不能以改名替代迁移。 |
| 业务名称与说明 | 供运维人员、Agent 和审计人员理解同一业务概念。 |
| 核心元对象锚点 | 可复用 `Person`、`RawMaterial`、`Product`、`Equipment`、`Store`，也可选择对象自身编码作为独立类型；供应商、采购订单不再默认归为人员。 |
| 受控来源与来源系统 | 明确对象来自哪个系统；“待观察”只是模板状态，不能发布。 |
| 业务主键与字段 | 支持跨系统关联、去重和字段级映射。 |
| 数据分级 | 作为权限裁剪和 Agent 证据输出的必要条件。 |

关系定义还应包含起点、终点、业务谓词、基数和证据来源。Semantica 候选关系仅表示已在合成事实中观察到共同业务标识；是否成为正式业务关系仍需运维人员确认。

## 当前已覆盖的语义对象

- OA 治理：组织、人员、岗位、业务角色、审批流程/节点/实例、待办、业务动作和审计。
- 跨系统演练候选：检验结果、质量事件、生产批次、库存、履约、审批实例和 CAPA。
- 核心锚点：人员、原材料、产品、设备和门店。

字段映射除既有 Mock 演练外，已有受信任服务端调用的受控样本验证入口。它不直接接收运营页面上传、不自动取企业数据；输入样本须先经过认证范围与字段脱敏。准备字段、协议、抽样上限和失败条件见 [样本映射接入指南](../development/SEMANTIC_DATA_CONTRACT_GUIDE.md)。样本验证通过不等于关系完整性、全量对账或发布通过。

## 发布与安全边界

- Semantica 返回给建模端的仅是字段结构、来源系统、图统计与关系证据数量；不会返回原始业务记录、权限信息或密钥。
- 权限中心仍决定谁能查看或编辑，语义模型本身不授予任何读写权限。
- 语义候选、草稿校验、模拟构建与版本发布是不同阶段。未经校验和发布的草稿不得被 Agent 当作生产事实或写入授权。
- 当前能力针对本机 Demo 与合成数据；生产接入前仍需完成字段字典、主数据映射、数据分级、角色裁剪、版本治理和审批签核。

## Semantica 生效状态

`GET /demo/model-definition` 只返回当前已登记模型的标识、版本、对象/关系数量和指纹。事实入图时会附带模型绑定状态：`mapped` 表示对象已匹配已发布定义，`unmapped` 表示事实未被该定义覆盖，`unconfigured` 表示尚无已发布定义。这些状态用于演示可观测性，不替代权限或业务审批。
