# ADR-001: 语义与权限分离

## Status
Accepted

## Context

企业 AI 平台需要同时回答两类问题：

1. **这个对象是什么？** 订单与入库单是什么关系？金额应按哪个粒度统计？字段含义与来源是什么？
2. **谁可以看？** 这个用户/角色/组织能否读取这批数据？能否发起动作？

如果这两件事由同一套机制决定，会产生难以修复的耦合：语义模型的建立者将隐式获得数据访问权；调整权限会迫使修改语义定义；两者无法独立演进。

项目在私有化企业场景下运行，客户的组织结构、数据分级、审批链差异极大，权限模型必须按客户适配，而语义定义应尽量保持稳定可复用。

## Decision

**语义层与权限层保持独立，各自演进，通过交集决定实际可见范围。**

- 语义模型描述对象、字段、关系、来源与口径；建立关系**不等于**扩大任何用户的数据范围。
- IAM 独立决定身份、角色、组织数据域、设备与会话约束；权限判定不依赖语义定义。
- 实际数据访问 = 语义模型定义的可用范围 ∩ IAM 授予的访问范围。
- 两者在领域目录上分离（`domains/iam` 与语义相关领域各自维护），并通过公共入口交互。

## Consequences

**变简单**：

- 语义模型可在不同租户/组织间复用时，不必携带权限配置；
- 权限策略可独立收紧或调整，不影响已发布模型；
- 元域智语人员可以建模而不获得业务数据访问权（安全默认值正确）；
- 审计上可清晰区分「谁定义了语义」与「谁读取了数据」。

**变困难 / 放弃的**：

- 需要两套概念体系，新人需同时理解「对象关系」与「访问控制」，学习成本更高；
- 每次数据读取都需同时校验两层，路径比单一校验长；
- 语义层无法「顺手」解决权限问题（例如不能在模型里直接声明「此字段仅财务可见」），这类需求需在 IAM 侧表达。

## 退出/复审条件

若出现以下情况应重新审议：

- 企业客户普遍要求「语义定义内置权限」，且维护两处被证明成本高于收益；
- 出现必须由语义层直接承载的合规要求（如按数据分类分级的字段级强制策略），且 IAM 无法表达。

在此之前，保持分离。
