# ADR-006: 双 Agent 独立入口

## Status
Accepted

## Context

平台服务两类职责差异极大的用户：

| 用户 | 核心任务 | 关键风险 |
| --- | --- | --- |
| 业务人员/管理者 | 用自然语言获得有证据的业务答案 | 越权读取、误以为已执行动作 |
| 语义/数据运营人员 | 把数据字典建成可发布、可校验的语义模型 | 未审阅即发布、错误口径进入生产 |

两者的授权语义、心智模型与安全边界完全不同：业务登录资格不应带来模型发布权；建模权限不应带来业务数据读取权。

同时，二者共享大量基础设施（身份、证据链、模型网关、治理），若拆成两套独立系统会造成重复建设。

## Decision

**提供两个独立 Agent 入口（智脑工作台、元域智语 Agent），二者共享服务端基础设施但保留各自的任务语义与授权范围；另设元域智营承担权限与运行治理。**

- 双端不合并为单一入口，也不做成「同一 Agent 换页面名称」；
- 共享：身份适配、IAM 校验、模型网关、证据链、审计、任务与通知基础设施；
- 分离：任务语义、授权范围、可用工具集、发布能力；
- 元域智营单独承担平台管理职责（此身份不是企业业务管理员）。

## Consequences

**变简单**：

- 安全边界清晰：业务入口无法发布模型，运营入口无法读取业务明细；
- 两端可独立演进能力与界面，互不牵制；
- 治理与审计可分别归因（谁在建模、谁在查询）；
- 共享基础设施避免了重复建设。

**变困难 / 放弃的**：

- 需要维护三套前端（智脑含多端、元域智语含独立 Electron、元域智营），多端一致性成本高；
- 用户需理解「我该用哪个端」，小团队/首个试用用户认知负担上升；
- 跨端协作（建模 → 发布 → 业务查询）需要显式交接，不能在一个界面内完成闭环。

## 退出/复审条件

- 若客户普遍反映「三入口」是采用障碍，可引入**单人实施模式**：一个身份在同一产品内切换视图可见性（业务/建模/管理），但**授权仍由服务端按角色裁决**——切换的仅是界面可见性，不是权限。这不违反本 ADR 的核心（授权分离），只是降低入口认知成本；
- 若出现必须由单入口完成的端到端场景（且安全边界可保证），需重新评估。

## 相关约束（不可破坏）

- 业务智脑与元域智语 Agent 是不同入口与授权场景，**不能用运营权限替代业务权限**；
- Semantica 的结构建议需人工校对，语义模型不能自行绕过发布治理；
- 业务登录资格 ≠ 模型发布权限；建模权限 ≠ 采购/库存/审批的操作权限。
