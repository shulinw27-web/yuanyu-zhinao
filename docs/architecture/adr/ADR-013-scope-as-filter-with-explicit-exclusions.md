# ADR-013: 建模范围是过滤器，被排除项必须显式列出

## Status

Accepted

## Context

### 当时的约束

- [ADR-012](ADR-012-explicit-modeling-scope.md) 把建模范围从「文本推断 + 空即放大」改为显式契约，并在**决策 5** 明确 **不按范围过滤对象**，理由是「过滤会让『材料里有、但范围外』的事实消失，而那通常意味着选择错了或材料传错了」。
- ADR-012 同时留下**退出条件 2**：若阶段 4 让范围开始裁剪对象（按选中系统抽取），则 `outOfScopeObjects` 的语义会从「材料与选择不一致的上报」变成「被过滤掉的记录」。届时必须重新决定：范围是**过滤器**还是**上报口径**——当时明确是后者。
- 阶段 3 的落地范围被有意限制为「只改『范围从哪来』，不改建模算法」，因此「过滤」这半被推迟到阶段 4。
- 用户确认的方案 4.5 决策是 **C = A（仅建模范围过滤）+ 超出角色数据域时明确阻断**。即「过滤」本就是用户已确认的意向，只是阶段 3 未落地。

### 触发点

阶段 4 要「按选中系统的字段目录/样本抽取对象与标识」。**抽取本身就是一次筛选**：未被勾选的系统没有字段目录，其对象无处抽取。范围由此从「标注口径」变成事实上的**过滤器**，ADR-012 退出条件 2 被触发。

### 需要回答的具体问题

运营勾选 **ERP + WMS**，上传的材料里同时含 **QMS** 的「来料检验记录」。这条内容怎么办？

三种候选：

- **纯过滤（静默）**：范围语义最干净，但运营忘勾 QMS 时看不到任何迹象，只会拿到一个「少了东西」的模型——这正是本次重构一直在消除的**静默**模式。
- **不过滤（延续阶段 3）**：信息不丢，但范围对提案几乎没有约束力，跨系统连接推导会把范围外对象牵进来。
- **过滤 + 被排除清单显式列出**：范围外对象不进提案，但单独列出「因未勾选而被排除」并提示补勾。

用户在 2026-09-25 选定第三种。

## Decision

### 1. 范围是过滤器

对象的来源系统**全部**落在所选范围之外时，该对象**不进入提案**。

### 2. 被排除项必须显式列出（本 ADR 的核心约束）

「过滤」不等于「静默丢弃」。被排除的每一项都必须以可读形式出现在任务结果里，让运营能立刻看出「材料里有东西因为没勾系统而被排除」，并据此补勾系统重跑。

| 情形 | 对象去向 | 上报字段 |
| --- | --- | --- |
| 全部来源在所选范围内 | 保留，计入 `covered` | — |
| **部分**来源在范围外（如 `ERP+WMS` 对象，只选了 `WMS`） | **保留**，计入 `covered` | `partialScopeObjects`（含 `outside`） |
| **全部**来源在范围外 | **排除** | `excludedObjects`（含 `sourceSystems`） |
| 来源为 `UNASSIGNED`（自然语言抽取未声明来源） | **保留**（来源未知即无法判断范围，排除等于静默丢材料） | `unassignedObjects` |
| 关系任一端点被排除 | **一并排除** | `excludedRelationships`（含 `reason`） |

两条边界规则的理由：

- **部分超出仍保留**：该对象有**合法在范围内**的来源，排除它会丢掉范围内系统的真实事实。越权/超范围的是它的**其他**来源，如实记入 `outside` 即可。
- **`UNASSIGNED` 一律保留**：把「来源未标注」当成「来源超范围」会让纯自然语言抽取路径（`semantic-natural-schema-service` 产出 `UNASSIGNED`）整体被清空，那是灾难性的静默丢失。

### 3. `outOfScopeObjects` 字段名移除

原字段「仍在提案中、但来源超出范围」的语义被拆成两个不同的事实：`partialScopeObjects`（**仍在**提案）与 `excludedObjects`（**已移除**）。保留 `outOfScopeObjects` 作为二者的并集别名会制造**两个真相**——调用方无法从字段名判断对象是否还在提案里。因此移除该字段名。

### 4. 排除产生「提示补勾」，不产生「自动放大」

被排除项**不**触发自动扩大范围，也**不**使任务失败。它只产生一条显式提示，由运营决定是否补勾系统后重跑。范围仍然只能显式给出（ADR-012 决策 1 不变）。

### 5. 排除发生在越权阻断之后

越权系统仍在**任务创建阶段整单拒绝**（ADR-012 决策 4）。范围过滤**不得**成为对越权系统的静默裁剪通道——顺序必须是「先越权阻断，后范围过滤」。

## Consequences

**变简单/变可靠**

- 「选系统」终于对提案有约束力，与用户确认的 4.5-A「仅建模范围过滤」一致。
- 阶段 4 的抽取器有了明确输入：只抽取范围内系统的对象。

**代价/变得更难**

- 被排除对象承载的业务事实**确实不再进入提案**。若某对象只有 QMS 一个来源而运营未勾 QMS，它就从提案里消失了——这是有意选择，缓解手段是显式清单 + 提示补勾，而不是把对象留在提案里。
- `excludedObjects` / `excludedRelationships` / `partialScopeObjects` 是**新的对外字段**，[`publicTask`](../../../backend/src/services/semantic-operations-task-service.js) 的字段白名单必须同步——ADR-012 已因遗漏白名单踩过一次坑（新字段内部有、接口返回 `undefined`）。
- 字段名 `outOfScopeObjects` 被移除，属**对外契约破坏性变更**（阶段 3 刚发布），调用方与测试需同步。
- 关系随端点被排除会**放大排除面**：一个被排除的核心对象可能带走多条关系。清单必须按「对象」与「关系」两类分别呈现，否则运营看到的关系缺失无法归因。

## 退出/复审条件

1. 若实测出现「被排除清单长期非空、但仍频繁产出不完整模型」，说明运营不会读清单——应改为在提案确认前做**阻断式提示**（先补勾再生成），而不是继续优化清单文案。
2. 若 `partialScopeObjects` 长期为空，说明对象极少跨系统标注，该字段可下线以简化契约。
3. 若阶段 6 的权限合并改变了角色数据域与按钮权限的关系，需重新核对「越权阻断**先于**范围过滤」这个顺序是否仍成立。
