# ADR-003: 状态与事实分离

## Status
Accepted

## Context

在 Agent 系统中，最容易被混淆的是「系统内状态」与「外部世界事实」：

- 页面出现了一段回复 → 系统状态，不代表业务事实已改变；
- 任务已排队 → 系统状态，不代表已执行；
- 审批已通过 → 组织决策状态，不代表业务动作完成；
- 外部系统已确认 → 这才是业务完成。

如果这些被合并表达（例如统一显示「已完成」），会造成严重后果：用户以为库存已冻结而实际上没有；运维以为发布成功而实际失败；审计无法区分「做过什么」与「声称做过什么」。

此外，企业系统调用的失败模式包括：超时但实际成功、返回不确定、重复投递。盲目重试会制造重复写入。

## Decision

**明确区分四类事实，任何一层都不得代替下一层；不确定结果进入只读对账，不通过盲目重试制造重复动作。**

事实层级：

| 层级 | 含义 | 可否对外声称 |
| --- | --- | --- |
| 已建议 | 模型产出建议/意图 | 只能表述为建议 |
| 已确认 | 用户完成一次性确认 | 表述为「待执行」 |
| 已审批 | 组织审批通过 | 仍不等于业务完成 |
| 已执行（含回执） | 外部系统/端侧返回成功回执 | 方可表述为完成 |

配套规则：

- 执行结果由服务端与端侧回执共同确认；
- 发布/写入等不确定响应进入**只读对账**，先查回执再决定是否重试；
- 幂等键保证重复请求不重复入账/重复创建；
- 页面状态、任务状态、业务状态分别展示，不合并为单一「完成」。

## Consequences

**变简单**：

- 审计与对账有明确依据，能回答「到底做没做」；
- 幂等与对账机制有清晰的设计目标（对治不确定响应）；
- 前端与提示语有统一的状态语义（可收敛为一套四态标签）；
- 用户不会因误导性完成态做出错误决策。

**变困难 / 放弃的**：

- UI 复杂度上升：不能用一个「成功」图标覆盖所有情况；
- 需要为每个副作用型操作设计回执、幂等与对账路径，工作量成倍增加；
- 文案要求更严格，产品与文案需理解四态差异；
- 长任务需要排队/暂停/取消/超时的显式状态机。

## 退出/复审条件

此决策**不建议退出**。它是本项目信任资产的技术基础。

仅在以下情形需补充而非取消：

- 引入新类型的外部副作用（如跨企业系统编排），需扩展事实层级，但不得压缩既有层级；
- 若某外部系统无法提供回执，应显式标注「不可确认」并降级体验，而不是假定成功。

## 相关约束（不可破坏）

- 「已生成建议」「已排队」「已写入文件」必须区分；
- 删除证据、改变发布时间或注入未知字段时，应检查拒绝/澄清与失效处理，而不只检查回答是否流畅。
