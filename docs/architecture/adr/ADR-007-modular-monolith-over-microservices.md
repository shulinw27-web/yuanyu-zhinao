# ADR-007: 保持模块化单体，不拆微服务

## Status
Accepted

## Context

系统包含：多端客户端（Web/Electron/移动 H5/钉钉 H5）、Agent Runtime、语义建模、权限治理、知识库、告警、风控、多租户与商业门户；后端 198 个文件、137 个 service；另有若干独立进程（Python 语义服务、多个 Worker）。

面对这种规模，常见的技术冲动是「拆微服务」。但当前约束是：

- **团队规模有限** —— 服务数量增长会迅速超出可维护的团队容量（每个服务都需要独立的部署、监控、版本与值班）；
- **业务边界仍在变化** —— 语义层的边界尚未稳定，过早固化服务边界会导致频繁的跨服务重构；
- **当前阶段不需要独立扩缩容** —— 单机 SQLite + 单节点部署即可满足现有验收；
- **已有合理的进程级分离** —— Python 语义服务经 HTTP 通信、Worker 独立进程，这些是**按运行时特性**而非按业务概念拆分，成本低且收益明确。

## Decision

**保持模块化单体（modular monolith）作为主形态，不引入微服务。**

- 业务能力以**模块**形式在单一部署单元内组织，通过 ADR-005 的分层与契约面约束边界；
- 仅在**运行时特性确实不同**时才分离进程：Python 语义服务（语言与库生态）、后台 Worker（长时任务与独立生命周期）；
- 服务间通信保持进程内调用（函数调用），不引入网络调用、服务发现、分布式事务。

## Consequences

**变简单**：

- 事务一致性免费获得：同一数据库事务内可保证多实体原子提交；
- 重构成本低：跨模块重构是「改 import」，而非「改协议 + 双端发布」；
- 调试与排障简单：单一进程、单一日志流、无分布式追踪需求；
- 部署简单：单一部署单元，无需编排与网关；
- 团队可全员理解整个系统。

**变困难 / 放弃的**：

- 无法按模块独立扩缩容（如需为语义建模单独扩容，只能整体扩容）；
- 故障域未隔离：一个模块的内存泄漏或死循环会影响整个进程；
- 技术栈统一受限（不能为某模块单独选语言/框架）；
- 随着规模增长，模块边界的纪律要求更高（这正是 ADR-005 棘轮机制的必要性）。

## 退出/复审条件（满足其一才考虑拆分）

1. **团队规模显著增长**（例如各领域有独立团队与独立发布节奏）；
2. **出现明确的差异化扩缩容需求**（某模块负载远高于其他，整体扩容不经济）；
3. **模块边界已稳定**（经历多个版本不再变动）；
4. **故障隔离成为硬要求**（单模块故障不得影响全局，且有明确 SLA）。

> **拆分的前置条件**：ADR-005 的契约面收敛必须已完成。若在边界未稳定、契约未成形时拆分微服务，只会把「扁平的 service 汤」变成「分布式的 service 汤」，复杂度上升而收益为零。

## 明确不做

- ❌ 不引入分布式事务、Saga 编排（无跨服务写入）；
- ❌ 不引入服务注册与发现（无动态服务拓扑）；
- ❌ 不为「将来可能要拆」而预留微服务抽象（YAGNI，且会污染当前代码）。
