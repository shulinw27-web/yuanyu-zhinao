# ADR-005: 领域分层与 public-api 契约面

## Status
Accepted（**含收敛目标**）

## Context

随着后端增长至 198 个文件、137 个 service，需要结构化的分层来避免「所有代码互相 import」。

已建立的分层：

```
routes/*.js  →  domains/*/public-api.js  →  services/*.js  →  repositories/*.js
```

现实情况（2026-09-24 实测）：

- **路由层纪律良好**：13 个路由文件全部只依赖 `domains/*/public-api.js`，且有 `architecture-boundaries.test.js` 守护；
- **领域层是名义的**：`domains/` 下 11 个目录中 9 个仅含一个 `public-api.js`，内容是**重导出清单**而非边界契约；
- **`public-api.js` 不减少耦合**：`governance` 导出 **92** 个符号、`agent` 导出 **61** 个，二者并非 bounded context，而是按路由倒推的目录；
- **服务层是扁平的**：137 个 service 通过相对路径自由互相 import，实测存在 **189 条跨领域依赖边**。

关键判断：当前 `public-api.js` 是「重导出管道」——导出即实现，调用方拿到具体实现，无法替换、无法 mock、无法约束。任何一行改动都可能影响路由。

同时必须承认：**分层本身是有价值的**，问题不在分层设计，而在于契约面尚未成形。

## Decision

保留并强化分层的**方向**，同时把 `public-api.js` 从「重导出清单」逐步收敛为**显式契约面**：

1. **方向约束（立即生效）**：`routes → domains → services → repositories` 单向；`routes` 不得 import `services`/`data`/`repositories`（已有测试守护）。
2. **规模约束（立即生效，棘轮）**：
   - 每个领域 `public-api.js` 导出数不得超过已登记基线，**只降不升**；收敛目标 ≤15。
   - 服务间跨领域依赖不得超过已登记基线（当前 189 条），**只降不升**。
   - 服务文件行数不得超过已登记上限，阻止 God Service 继续膨胀。
3. **收敛路径**：新增领域间调用必须经对方 `public-api.js`；既有跨域边逐步迁移，每迁移一条即下调基线。
4. **基线单一事实源**：所有基线登记在 `backend/test/architecture-baseline.js`，可用 `node scripts/architecture-baseline.mjs` 重新测绘；**刻意不提供自动写回**，以防「为让测试通过而放宽基线」。

> 说明：导出数 15 是目标值而非当前约束；棘轮机制保证不会恶化，并允许分步收敛。

## Consequences

**变简单**：

- 架构约束从「人工纪律」变为「测试期强制」，新增违反会直接失败；
- 基线可测量、可复现、可审计，收敛进度可见；
- 为后续拆解 God Service 提供守护网（先有约束再重构）；
- 新人可从测试文件直接读到架构规则。

**变困难 / 放弃的**：

- 新增跨领域调用需要显式走 public-api，短期有改造摩擦；
- 棘轮基线需人工维护（每次收敛后下调），忘记下调会导致测试失败——这是刻意的提醒机制；
- 部分既有跨域边（189 条）客观上合理（如 `local-model-gateway` 调用各契约模块），强行消灭会引入不必要的间接层，因此采用「冻结+允许」而非「一律禁止」。

## 退出/复审条件

- 若某领域确实需要 >15 个对外能力，说明该领域应**拆分**而非放宽上限；
- 若棘轮维护成本高于收益（例如团队规模扩大后），可改为按季度评审的软约束；
- 若引入模块系统（如 package 级边界强制），可由更强的机制替代本测试。

## 相关约束（不可破坏）

- 路由层不得重新穿透扁平服务层；
- 组合根（`app.js`）保持 ≤140 行且不承载业务路由；
- 前端通过页面注册表与动作控制器组织业务。
