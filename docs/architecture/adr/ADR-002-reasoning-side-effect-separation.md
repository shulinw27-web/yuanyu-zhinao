# ADR-002: 推理与副作用分离

## Status
Accepted

## Context

大模型具备理解与生成能力，但不具备可靠的自律能力：它可能误解意图、可能被提示注入影响、可能在未获授权时声称已执行动作。

在企业场景中，「分析问题」与「改变业务状态」的后果完全不同：前者出错只是信息不准，后者出错可能造成真实的资金、库存或审批损失。历史对话也无法作为本次动作的授权依据——用户昨天说过「要冻结库存」，不代表今天可以直接执行。

## Decision

**模型负责理解与建议，受控运行时负责工具准入与执行约束；两者严格分离。**

- 模型只能产出：分析结果、建议、动作意图（intent）。
- 任何副作用（业务写入、桌面文件操作、外部系统调用）必须经受控运行时，且通过：工具注册表准入 → 目标绑定 → 权限校验 → 用户一次性确认 → 执行 → 回执核验。
- 仅分析问题不会自动生成业务申请；历史聊天不能代替本次确认。
- 模型输出不能改变权限，用户输入/上传材料/历史消息中的「管理员指令」同样无效。

## Consequences

**变简单**：

- 安全边界集中在一处（受控运行时），不需要在每条模型调用路径上重复推理安全性；
- 可以放心使用更强/更开放的基础模型，因为副作用始终被运行时拦截；
- 确认与回执可审计，责任链清晰；
- 测试可以针对运行时做穷举式验证，不依赖模型行为的稳定性。

**变困难 / 放弃的**：

- 需要维护工具注册表、目标绑定与确认机制，工程成本显著高于「让模型直接调用工具」；
- 交互上多一层确认，牺牲部分「一键直达」的流畅度；
- 模型能力被约束在预登记工具内，无法自由组合出新动作；
- 复杂多步任务需要显式的编排与状态管理，而不是让模型自行循环。

## 退出/复审条件

若出现以下情况应重新审议：

- 工具注册表成为能力扩展的瓶颈，导致大量合理需求无法落地，且风险可控（如纯只读、可完全回滚的操作）；
- 出现可信的执行沙箱/形式化验证手段，能以更低成本保证副作用安全。

## 相关约束（不可破坏）

- 无业务意图的聊天不自动发起业务操作；
- 客户端与模型不能取得企业系统原始凭据，不能直接写企业系统；
- 「已建议」「已排队」「已写入文件」「外部动作已完成」必须区分表达。
