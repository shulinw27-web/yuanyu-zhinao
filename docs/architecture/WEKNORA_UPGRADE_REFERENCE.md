## 1. 为什么参考这个项目

我们的主要建设方向是“语义运营建设业务模型，智脑使用模型理解和处理业务”。已经形成材料工作区、候选对象与关系、人工审阅、模型发布、有界跨系统查询、证据解释和受控执行等能力，但通用企业知识接入与检索仍需要补强。

WeKnora 围绕企业文档构建知识检索、问答、Agent 工具使用和知识管理，具有多模态解析、混合检索、Wiki、跨会话记忆等功能设计。它提供了值得参考的知识产品建设路径，但文档列出的能力不等于已经在我们的数据、部署环境和安全要求下通过验收。[官方介绍](https://github.com/Tencent/WeKnora/blob/main/website-docs/01-getting-started/01-introduction.md)

本方案的判断是：保留现有语义层和业务执行核心，吸收其知识接入、检索、知识运营和 Agent 交互设计。先验证收益，再决定复用服务还是自行实现，不先做整体替换。

## 3. 已采纳的设计方向

P0 表示应先验证和建设的基础项；P1 表示依赖基础项或适合后续完善的内容。以下均为本方案建议，未更新为生产完成状态。

| 编号 | 优先级 | 参考并采纳的方面 | 我们计划升级的内容 | 为什么这么做 |
| --- | --- | --- | --- | --- |
| WK-01 | P0 | 文档连接器与同步生命周期 | 统一资料接入、版本、失效、重试、索引状态 | 企业制度和接口文档持续变化，一次上传不能保证长期正确 |
| WK-02 | P0 | 混合检索、融合排序与重排 | 精确编号、词法与向量召回联合使用 | 兼顾业务编号准确性和自然语言表达变化 |
| WK-03 | P0 | 分块预览和结构化文档处理 | 原文、解析内容、候选模型及引用联动校对 | 让人能够定位并纠正解析错误，避免错误进入模型 |
| WK-04 | P0 | 快速问答与多轮工具模式 | 普通对话、知识问答、业务查询和执行请求分流 | 简单问题降低不必要开销，复杂问题能补查证据 |
| WK-05 | P1 | 可编辑、有来源的 Wiki | 建模前生成业务理解草稿，人工校验后再转模型候选 | 降低运营人员理解材料的成本，同时保留正式模型门禁 |
| WK-06 | P1 | 明确记忆与自动提取分离 | 建设记忆确认、修改、拒绝、删除和冲突处理体验 | 防止一次误解变成长期错误，也让用户知道系统记住了什么 |
| WK-07 | P0 边界、P1 管理完善 | API Key 能力范围与知识库授权 | 在接入前完成身份与资源隔离，随后完善多团队管理 | 文档可检索不等于所有用户都能看；授权必须覆盖索引、引用与缓存 |
| WK-08 | P0 基线、P1 运营面板 | 模型追踪、审计与任务观测 | 记录解析、检索、重排、生成的质量和性能 | 有依据地判断瓶颈及升级收益，而非凭回复长短判断智能程度 |

### 3.1 WK-01：让文档持续进入系统

WeKnora 将连接器、调度和知识入库分开，支持来源范围、同步计划、增量比较以及失败日志；删除检测和恢复能力因连接器而异。[数据源设计](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/10-datasource.md)

我们拟统一记录来源文档 ID、版本或内容指纹、更新时间、业务生效区间、所属企业、可见范围、解析版本和索引状态。先接入已有上传材料，再按真实企业需要增加钉钉、飞书或其他文档源，不能把登录渠道适配当作知识源已经接通。

同步失败时保留失败状态与可重试位置；删除或撤权后，相关索引、缓存和引用入口必须同步失效。旧版本可按归档策略保留，但只能在授权历史查询中使用，不能悄悄混入“最新制度”。

### 3.2 WK-02：升级检索，不替代业务查询

WeKnora 将关键词与向量结果分别召回，再通过 RRF 按排名融合；只有单路结果时保留该路分数并去重。该行为已核对 [融合源码](https://github.com/Tencent/WeKnora/blob/081851c6b8802225ae968ba67d8de444e258c67b/internal/application/service/knowledgebase_search_fusion.go)。引擎能力及配置见 [检索文档](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/05-retrieval-engines.md)。

建议链路为：授权范围内筛选 → 业务编号精确匹配与词法/向量召回 → 融合去重 → 按需重排 → 补充相邻或父级上下文 → 来源复核。重排是否值得默认启用，需要比较正确率、耗时和成本。

“原料不合格怎么处理”可以检索 SOP；“这批原料影响多少订单”必须走已发布业务模型和受控数据查询。库存、数量、金额及责任关系不能用相似文档代替实时事实。

### 3.3 WK-03：让多模态解析可以被核对

WeKnora 提供分块预览、按结构选择分块策略和父子分块；调整配置后需要重新解析存量文档。[分块设计](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/04-chunking.md)

语义运营端建议采用“原始材料—解析结果—模型候选”联动视图。PDF 引用尽量定位页码和区域；表格定位工作表、表头及单元格；图片保留原图与识别内容的关系。无法定位时明确显示只有文档级来源，不伪造精确坐标。

人工修正需留下版本差异，并标明需要重新解析、重建索引或重新审核的模型资产。模型不能因为文档被修改就自动覆盖已发布定义。图片和扫描件继续执行现有多模态出网、文件安全与权限限制。

### 3.4 WK-04：让 Agent 根据任务选择处理路径

WeKnora 区分快速问答和智能推理，后者允许多轮调用，并可配置工具范围、最大迭代和调用超时。其文档描述的人工工具审批针对 MCP 工具，不能推断所有写操作都已有同等审批。[Agent 引擎](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/07-agent.md)

我们建议保留统一对话入口，在内部区分普通交流、知识查询、实时业务分析和执行请求。只有缺少必要信息时才澄清；“这是什么意思”“给我一个方案”等追问应结合任务对象和前文证据理解，不能再次当成空白任务。

复杂分析允许在授权工具范围内补查，并设置总时限、调用次数、重复查询检测、费用预算及取消机制。遇到数据不足时返回已确认结论和具体缺口；遇到授权不足时说明边界。不能通过反复调用消耗预算后假装任务完成。

前端显示正在查哪些系统、读取哪些资料、缺少什么及是否等待授权，展示可核验的执行摘要，不要求公开模型内部思维链。任何实际写入仍需符合原有计划、确认、执行回执和审计协议。

### 3.5 WK-05：Wiki 作为业务理解草稿

WeKnora 将资料整理成带引用、相互链接的页面，允许人工编辑、版本比较和回滚。[Wiki 设计](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/14-wiki.md)

我们可借鉴生成采购流程、批次概念、部门职责、指标口径等主题草稿。每个条目关联材料版本，区分原文事实、模型推断和人工确认。材料之间矛盾时并列展示，不替用户选择权威版本。

进入语义层时仍要转换为对象、主键、关系、来源映射、指标及规则候选，再通过人工审核和用例回放。Wiki 页面链接不等于数据库外键，自动提取关系不等于业务因果，解释文档也不等于可执行读计划。

### 3.6 WK-06：完善长期记忆的治理与体验

WeKnora 支持明确记住与自动提取两种模式，推断内容可先待确认，用户可以编辑、拒绝、删除和清空。记忆按空间及调用者隔离，不扩大知识访问权限。[记忆设计](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/23-memory.md)

我们保留现有结构化记忆机制，补充可见管理入口。用户偏好可长期保留；任务状态需要跟随任务更新；业务事实只保留来源引用并按时效重新查询。自动推断的长期事项应可确认，手工修正不应被后台提取静默覆盖。

删除错误记忆后，应避免继续从旧对话重复抽取同一错误；保留何种抑制标记及多久，需要在隐私和保留策略中明确。跨会话记忆不等于训练模型，本阶段不开展权重微调、不自动把员工对话用于训练。

### 3.7 WK-07：身份、资料与工具范围贯穿整条链路

WeKnora 将 API Key 的能力范围、知识库范围与用户角色区分，并提供组织共享及资源归属控制。[权限设计](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/01-tenant-auth.md)

接入时由我们的后端负责映射身份及已授权资料范围，不能由客户端自行声明企业或知识库访问权。优先使用最小权限服务凭据，不将管理密钥交给前端，也不能通过单个无限制密钥把全库结果传给模型后再过滤。

授权检查至少覆盖召回、原文读取、引用下载、缓存命中及返回答案前的有效性检查。员工离职、部门调整和共享撤销后必须验证失效行为。外部资料中的指令始终作为资料，不得修改系统提示、授权规则或工具权限。

### 3.8 WK-08：以效果和证据决定是否升级

WeKnora 的观测设计包含请求关联、模型调用追踪、用量、审计和后台任务队列。[可观测性文档](https://github.com/Tencent/WeKnora/blob/main/website-docs/03-features/16-observability.md)

我们在现有证据链上增加解析耗时、各路召回数量、重排耗时、模型调用次数、输入输出用量和完整响应时间。链路日志默认避免记录完整敏感原文，调试采样需要独立授权和保留策略。

建议建立检索与答案分开的评测：先判断正确证据是否被找到，再判断答案是否被证据支持。流式输出改善等待体验，但首段到达不等于完整任务完成，两类时延必须分别统计。

## 4. 建议的总体架构

```text
智脑：用户问题 + 会话上下文 + 当前有效身份
                   │
            请求理解与授权路由
                   │
       ┌───────────┼───────────┬────────────┐
       ↓           ↓           ↓            ↓
    普通对话    制度/资料问答  实时业务分析    执行请求
    对话模型    知识服务       已发布语义模型  计划与授权确认
                检索/原文     受控系统查询    受控执行器
                文档版本证据  业务事实证据    执行回执
       └───────────┴───────────┴────────────┘
                   ↓
           核对来源与状态后生成回答

语义运营：资料接入 → 解析校对 → 业务理解草稿/Wiki
                    → 对象与规则候选 → 审阅/回放 → 发布语义模型
```

知识服务、语义查询和执行器均沿用当前权限边界，不因路由选择而提升权限。需要同时回答制度和事实的问题可以组合两条只读路径，但必须区分证据类型与时间。

以“这批原料异常影响哪些门店，应该怎么办”为例：语义查询追踪采购、投料、成品、调拨及销售关系；知识服务检索当前有效处置制度；智脑分别说明实际影响、制度依据、推断建议和未覆盖范围。创建调查或发送通知属于新的执行步骤，不能把分析请求视为已经授权。

| 方式 | 优点 | 代价与限制 | 本方案意见 |
| --- | --- | --- | --- |
| 独立部署 WeKnora，通过服务接口接入 | 能较快验证现成解析、索引和管理功能 | 新增部署与升级责任，需打通权限、引用和数据生命周期 | 优先用于隔离试点，效果通过后再决定生产采用 |
| 借鉴设计，在现有服务内实现 | 与当前数据归属、审计和语义流程一致 | 需要自行承担解析、检索和知识管理建设 | 保留为方案，按试点差距分步实现 |
| 整体替换现有 Agent 或语义层 | 可统一到另一套产品框架 | 已有业务协议、执行门禁和模型发布流程需要大幅重做 | 当前不采纳 |

第二批已建立内部提供方的 `search/read/status` 契约和本地实现，并完成 WeKnora 只读适配代码；运行时仍仅使用本地资料。以下为完整目标职责，不能全部视为已完成，也不是 WeKnora API 的真实命名：

- 检索：输入问题、有效主体、授权资料范围和版本约束，输出带来源标识的片段。
- 原文读取：按文档及片段标识再次校验权限，返回可引用的内容与定位信息。
- 同步状态：返回来源版本、解析/索引状态、失败原因与失效信息。
- 证据元数据：区分资料版本、生效时间、读取时间、索引版本和权限上下文。

优先获得原始检索片段，由智脑统一组织答案。直接调用第三方完整问答接口可能引入两次生成、重复成本和来源损失；是否使用需专项验证。更换知识提供方不应改变业务执行的授权与回执协议。

正式集成前仍需决策：部署形态、选定版本、解析器与检索引擎、Embedding/Rerank 模型、现有方舟模型的适用任务、网络及出网限制、资料存储位置、备份恢复和版本迁移方式。复用源码前核查所选版本的许可证及依赖声明；本方案不构成许可证兼容性审计。

## 6. 实施顺序与阶段产物

本节描述阶段依赖，不另建一份生产完成清单。进入实际开发后，生产待办统一在 [生产 Checklist](../operations/PRODUCTION_TODO_CHECKLIST.md) 维护，结果链接到独立测试记录。

| --- | --- | --- | --- |
| A：冻结基线 | 整理代表性资料、问题、角色和人工标准答案；记录当前链路结果 | 数据集版本、证据标注、基线报告、验收口径 | 基线可重放，预期答案及权限边界明确 |

## 7. 验证内容与验收思考

先使用合成或已授权脱敏材料，不把当前测试通过描述成生产客户效果。拟选三类场景：制造供应链异常、跨仓履约与财务核销、人员职责和制度查询；已有供应链材料可从 [场景文档](../development/SUPPLY_CHAIN_INCIDENT_SCENARIO.md) 复用。

| 验证面 | 代表问题或操作 | 检查重点 |
| --- | --- | --- |
| 同义表达 | 用不同说法询问同一质量处置制度 | 是否召回同一有效依据，而不是只命中特定关键词 |
| 精确目标 | 相似批次编号、相邻订单、同名不同系统对象 | 不串目标，不以相似度覆盖显式编号 |
| 多模态 | 扫描 PDF、跨页表格、图片与 Excel 联合说明 | 内容、表头、单位、币种和来源位置是否保留 |
| 多轮上下文 | 先分析异常，再问方案、责任人、另一批次 | 延续正确对象，切换目标后不沿用错误证据 |
| 版本冲突 | 旧 SOP 与新 SOP、相互矛盾的 API 文档 | 明确版本、生效时间和冲突，不擅自合并 |
| 动态权限 | 撤销共享、用户换部门、跨企业访问、直接打开引用 | 召回、原文、缓存及生成结果均不泄露 |
| 联合业务 | 查询影响范围并要求按制度给建议 | 实时计算与文档依据分别溯源；建议不冒充执行 |
| 记忆纠错 | 错误推断待确认、修改偏好、删除记忆 | 未确认不当事实使用，删除后不继续生效 |
| 故障与攻击 | 解析失败、模型超时、重复调用、文档提示注入 | 有界停止、真实状态、可恢复且不越权 |

量化时分开报告证据召回率、引用支持率、答案正确率、上下文承接成功率、误拒绝率、越权泄露数、P50/P95 完整响应时间及单次费用。样本较少时列出逐次数据，不据此宣称稳定生产分位数。

对照应使用同一资料版本、问题、身份和生成模型设置，交替运行并记录缓存、超时及重试。先比较检索结果，再比较最终答案，避免把模型差异误判为检索收益。质量提升阈值和成本上限在阶段 A 固定，不看完结果后调整标准。指定的权限负例必须全部通过，但有限样本零泄露不等于完成安全审计。

## 8. 明确不采纳及后续思考

当前不采纳：以文档图谱替代正式业务本体；用 RAG 估算订单和财务事实；让自动 Wiki 更新直接发布模型；把记忆当授权；给 Agent 无限制工具调用；把框架接入或回归数量当成智能水平证明。

后续需要持续回答的设计问题：

1. 哪些知识应留在文档层，哪些必须转成可校验的模型规则？判断依据是是否参与业务计算或执行，而不是是否能被大模型提取。
2. 知识发生变化后，如何提示受影响的模型、流程和历史答案？应建立依赖关系并发起复核，不自动改写已批准业务规则。
3. 多份资料谁更权威？需要版本、生效时间和企业明确的来源优先级，模型不能自行决定。
4. 何时多轮查证真正有收益？依据新增证据及问题解决情况停止，而不是只按固定轮数运行。
5. 哪些能力值得复用外部框架？由同条件效果、权限契合度、维护成本及可替换性决定，不由功能数量决定。

首次方案交付仅包含升级参考及文档入口。后续开发范围与测试以本文开头的实施记录为准；未完成项仍需按上述阶段执行。
