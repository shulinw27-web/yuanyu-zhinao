# 主数据对照映射执行指南

## 明确多跳链路与Mock验证（2026-10-10）

同一读取计划可以逐数据集声明多跳映射，不需要把编号当成相同实体。已新增合成ERP→MDM对照→WMS→另一MDM对照→POS链路，以及POS→WMS→ERP的明确反向读取回归。两张对照分别校验各自版本、有效期和确认状态，图证据保留每跳业务关系方向；结果只覆盖声明计划，不代表全企业事实。

例如ERP原料`ERP-001`通过`map-v1`匹配仓库`SKU-900`，再通过`sales-v1`匹配门店商品`POS-77`。合成样本返回库存42件、关联销售额120元；这些是Mock断言，不是真实企业数据。第二跳缺失、未确认、过期或多条有效映射时整单失败，不读取POS，也不返回已算出的部分财务结果。全部目标和对照对象先做权限预检，第二张对照无权时第一次源请求也不发起。

这验证已有的显式有限多跳能力，不是新增任意递归或自动路径发现。每一跳仍须配置前序数据集、对应字段、唯一声明关系、映射对象及`asOf`；现有读取计划最多24个数据集。脚本、动态URL、自动实体等价和任意映射依赖的递归展开仍拒绝。

服务端映射绑定现与客户端采用相同的属性允许列表：只允许predicate、objectType、fromField、toField、statusField、versionField、validFromField、validToField、asOf和direction。夹带script、url、recursive、maxDepth等扩展直接报`READ_MAPPING_BINDING_INVALID`，在读取源系统前失败；不再静默忽略这些配置。允许列表不会开放脚本执行。

适用范围：已发布模型的有界只读计划。当前支持版本化、人工确认的主数据对照表；不执行补零、脚本、SQL或外部URL，也不写回ERP/WMS。

## 场景

ERP原料编号是 `ERP-001`，WMS编码是 `SKU-900`。不能直接把ERP编号传给WMS，也不能因为两边恰好同值就认定是同一实体。需要声明并授权读取对照对象，再按其有效版本转换查询值。

操作步骤：建立对象和对照字段 → 为业务关系声明映射 → 在读取计划绑定对照对象 → 人工审核与正反例回放 → 发布 → 智脑选择方案读取。映射对象的授权由平台IAM配置，模型不能自行授予。

## 模型与计划契约

### 在界面配置

进入模型校对，展开“按需修改对象、关系和技术映射”，再展开“跨系统编码不同？配置主数据对照”。向导默认折叠，不占用主模型图的审阅空间。

1. 选择业务关系，再选择正向或明确标注“反向查询”的现有读取步骤。没有步骤时，先在“智脑关联查询与计算”导入或起草方案；向导不会自动创建方案。
2. 选择已有、单来源的对照对象，指定源编码、目标编码、确认状态、版本、生效和失效六个字段。列表只显示已有两端引用的对象；没有候选时补充对照数据字典，或让运营Agent起草对象后人工核对。两端编码字段须在对象定义里明确引用业务字段，字段名相似不算引用依据。切换读取步骤会清空旧对照选择。
3. 填写维护人、映射版本及固定UTC有效时点，核对转换路径。若多个步骤共用此关系，提示依赖数量；本次只绑定选定步骤，其他步骤需逐一核对，不自动改写。
4. 点击“应用到本地候选”，再保存、服务端校验、正反例回放和发布。应用不发送业务查询，不修改公式或平台授权，可使用工作区撤销恢复。

模型或权限改变会清空向导待配置内容；旧草稿候选不能应用到新模型，只读角色无法应用。读取步骤摘要会注明经哪张对照对象转换，不把映射步骤写成普通同值连接。导入方案预览也会拒绝缺字段、无效日期、任意URL对象名及附带脚本等不支持的映射形状；服务端依然负责最终契约及权限验证。

业务关系示例：

```json
{
  "from": "Material",
  "to": "Stock",
  "predicate": "stored_as",
  "cardinality": "1:n",
  "keyMapping": {
    "fromField": "id",
    "toField": "sku",
    "basis": "master_data_lookup",
    "lookupSource": "Crosswalk",
    "owner": "主数据维护岗",
    "version": "map-v1"
  }
}
```

`Crosswalk` 必须是模型中已声明的单来源对象。其 `erp` 字段引用 `Material.id`，`wms` 引用 `Stock.sku`；另有主键 `id`、确认状态 `status`、版本 `revision`、有效起止 `start/end`。所有这些字段必须在对象字段列表和平台允许读取的字段中。

读取计划中，根数据集 `material` 按用户指定的 `Material.id` 查询；后续 `Stock` 数据集的 `where` 条件如下：

```json
{
  "field": "sku",
  "dataset": "material",
  "sourceField": "id",
  "mapping": {
    "predicate": "stored_as",
    "objectType": "Crosswalk",
    "fromField": "erp",
    "toField": "wms",
    "statusField": "status",
    "versionField": "revision",
    "validFromField": "start",
    "validToField": "end",
    "asOf": "2026-10-09T00:00:00Z"
  }
}
```

`asOf` 是方案显式固定的UTC有效时点，不默认当前时间，不代表实时同步。`status` 必须为 `confirmed`；`revision` 必须与关系的版本完全一致。起止采用UTC ISO时间，有效区间为左闭右开，`end: null` 表示无截止时间；记录来源时间不得晚于有效时点。日期规范化后不一致、起止倒置等无效时间拒绝。当前严格拒绝返回行中的错误版本；连接器应提供符合计划范围的版本化对照数据。

每个源编码在有效时点必须恰有一条确认对照。重复活跃对照即使目标相同也拒绝，避免掩盖重复维护。一个目标编码可以对应多个库存记录，但至少要读取到一个目标；过滤后没有目标也会失败，不用缺失映射或缺失库存记录冒充零库存。

## 反向查询

从WMS库存查询ERP原料时，在上述 `mapping` 中显式加入 `"direction": "reverse"`，读取条件使用库存编码作为源值、原料编号作为目标字段。`fromField: erp`、`toField: wms` 仍按关系定义方向填写，不反写对照字段。省略direction仍是正向，不会自动猜测或降级为反向；其他值拒绝。

反向查询仍校验两端字段引用、IAM、确认状态、版本和有效时点。每个目标侧编码必须恰有一条有效确认对照；同一个WMS编码对应多个ERP编号时拒绝，不能随意选择或展开。查询可以反向，但实例图证据仍保留原已声明业务关系方向。递归映射和规则脚本不在本功能范围内。

## 权限与证据

首次查询前会校验原料、库存和对照对象的全部对象/字段授权。对照记录经过租户、组织、来源系统、数据分级、主键和字段类型准入；每次查询与返回前重验。查询预算仍为60秒、64次请求、500条总记录、单次100条，新增映射业务对最多2000对。

成功执行后，服务端生成本进程可验证的映射证据，绑定完整模型内容及本次授权记录快照。实例图显示“快照内已通过确认的主数据映射关联”，依据包含映射版本和有效时点。客户端伪造、JSON恢复的标记、记录修改或模型修改不能复用该证据；刷新后重新查询。它不替代当前权限检查，不是持久化审批回执，也不能证明业务因果或完整影响范围。

只声明 `keyMapping` 而没有执行绑定时，仍不能通过底层外键等值连接绕过。正向和反向均须显式计划绑定、校验与回放；递归图扩展尚不支持转换映射，保持拒绝。其他映射依据类型仍可作为建模声明，但不在本执行器支持范围内。

## 验证与限制

`npm run test:ontology` 包含ERP→MDM→WMS测试：原料 `ERP-001` 转为 `SKU-900` 得到42件库存；草稿保存保留映射，错误定义拒绝且不改变指纹；正反例回放后使用Mock部署回执发布，再通过Mock HTTP连接器驱动已发布智脑查询和实例图。

反例包括缺失、未确认、重复活跃、过期、错误版本、未来来源时间、目标缺失、跨租户以及查询期间撤权。反向Mock回归覆盖查询字段倒转、读取结果、原方向证据、漏填/非法方向和重复对照拒绝。可视化向导已通过状态、模板编译、服务端契约与Mock读取测试；反向候选和方案导入由真实Vue组件测试覆盖。此前浏览器隔离组件验证390px及1366px无横向溢出，未点击不产生应用事件，点击只生成本地候选，只读时禁用。企业系统和真实大模型均未验收；模型发布、授权和真实连接器接入需各自验收。
