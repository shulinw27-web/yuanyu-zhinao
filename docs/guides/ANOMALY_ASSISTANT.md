# 异常助手：消息理解、提报人确认与结构化记录

更新：2026-09-14。当前为第一阶段试运行功能，不是钉钉全群监听或正式质量管理系统。

## 解决什么问题

员工用文字、照片或口述报告异常时，信息通常不完整，还会补充、更正。异常助手把这些材料整理成可校对的字段，并保留来源和版本。比如“二车间3号灌装机漏液，估计二十多箱受影响”，影响数量应保留“估计二十多箱”，不能变成精确的20箱；员工说“已停机”也不等于MES提供了停机回执。

## 当前可用范围

| 能力 | 当前状态 |
| --- | --- |
| 智脑桌面前端、移动端、钉钉H5入口 | 共用工作台新增“异常助手”；手机底栏为“异常” |
| 人工文字、模拟群消息、人工转写文本 | 可新建草稿或补充到明确选中的记录；模拟群消息不冒充已验证钉钉来源 |
| 图片/PDF | 每次一个、最大4MB，复用已有安全检查与OCR/视觉解析；不可解析则拒绝，不生成假观察 |
| AI解读与分析 | 字段原话、带引文的消息理解、可能风险、处理建议与追问；解释不等于核实事实。需管理员允许和用户逐次确认；真实方舟效果尚未通过 |
| 提报人回复与确认 | 本站原提交者可回复指定确认请求；@消息只生成预览，没有发送到钉钉。回复更正后重新整理，再确认最新版本 |
| 人工校对、确认、撤回 | 已实现，保留更正原因和历史版本；补充或重新提取后回到草稿 |
| 身份和存储 | 当前企业、主体及原始角色隔离的个人工作区，不是企业共享收件箱 |
| 内部事件 | 记录变化与事件Outbox原子保存；事件只含编号、版本、状态和动作，不含汇报正文 |
| 钉钉Stream/群回调、原生录音与ASR | 尚未接入；页面不接收音频二进制，人工转写有明确标记 |
| 已发布业务对象匹配、影响范围分析 | 尚未接入异常助手；设备/批次字段只是报告文字，不是已核验的台账绑定 |
| ERP/MES/QMS写入和群卡片回执 | 尚未接入；确认汇报不会冻结库存、停机、建单或发群消息 |

当前不自动把汇报写进WeKnora，也不注入普通聊天记忆。异常记录与已发布世界模型的关联消费属于后续工作，不能仅因已有事件基础就声称智脑已经能基于新异常计算影响范围。

## 如何使用

1. 启动更新后的后端与智脑端，在功能导航打开“异常助手”。已运行的旧服务需要重新加载代码；仓库更新不会自动重启服务。
2. 选择来源并填写原文。录音暂时先人工转写；不要选成“AI语音识别”。可附一张照片或PDF，并确认允许企业已配置的OCR/视觉服务解析（可能出网）。
3. 点“新建异常草稿”。这一步只保存来源，没有模型识别或业务执行。需要承接之前的汇报时，先选中记录，再点“补充到选中异常”。
4. 服务端已开放模型时，检查模型名称，勾选本条异常资料出网确认，点“AI解读与分析”。字段逐字摘录；AI理解、风险和建议另行显示并附引文。问题单独列出，来源不匹配或非法结构会拒绝整次结果。
5. 核对地点、设备、批次、异常现象、影响数量、发生时间、已采取措施。缺失值留空；消息接收时间不等于发生时间。填写更正原因，保存字段更正。
6. 点“生成 @ 提报人确认请求”，阅读当前字段、AI理解和待补充问题。当前只生成站内请求及未发送的群消息预览；提报人绑定本站已认证提交者，不能从粘贴消息中的姓名推断。
7. 有误时，在“提报人补充 / 更正”填写回复，点“提交本人回复，重新整理”。回复保存为新来源并使原分析过期；重新AI解读，或保存人工校对，再生成新的确认请求。“好的、同意”也是普通回复，不会自动确认。
8. 核对无误后，勾选本人核对声明，点“本人确认本版本汇报”。地点与异常现象为最小必填项，其余未知可保留。确认只针对汇报信息，不认可所有AI推测、不授权业务执行。表单或回复框有未提交内容时不能误确认旧信息。
9. 查看来源、历史和结构化结果。补充、新的AI解读或字段更正都会使原确认失效。撤回后只读，不允许继续编辑或解读。

异常来源保留文本、接收时间、来源类型和摘要指纹。图片解析结果单独标为material_observation；它既不是汇报人的原话，也不是视觉事实已核实。原始图片/PDF二进制不保存在异常库，请在企业文件管理处另行保留；哈希不能代替原文件回看。历史版本中的sourceId对应来源列表中的id。

## 模型配置和权限

默认禁止把异常资料发送模型。使用现有方舟配置时，仅在需要启用的后端进程设置：

```powershell
$env:ANOMALY_MODEL_ALLOWED_MODES = 'ark'
npm run start:ark
```

不要把密钥写进此文档或源码。该变量只是额外的用途开关，不能替代原模型白名单、预算和企业数据出网审批。每次提取还会核对用户确认的provider/model；调用中策略、权限或记录版本变化，结果丢弃。模型单次最多45秒，不自动无限重试，不把降级模板当作已识别字段。

附件解析走原有OCR/视觉配置及安全策略；上述变量仅控制后续字段提取，不会自动开启图片原图出网。使用者必须分别确认附件解析和字段提取。

接口沿用已认证会话：读取需要page.agent.view，创建/更正/提取/确认/撤回还需agent.prompt.run。个人汇报确认不等同质量经理审批。身份来自服务端，客户端不能传入管理员、企业、群成员或验证过的钉钉来源来扩权。

每个个人工作区最多64条记录、每条20个版本、12项来源、来源正文合计24,000字符，工作区最大2MB。达到限制拒绝新增，不悄悄截断。当前撤回是逻辑撤回，不是物理删除；生产留存期限、清理及法律保全策略需单独建设。

## 接口与数据契约

统一前缀`/api/agent/anomalies`，不提供匿名机器人Webhook。

| 方法和路径 | 用途 |
| --- | --- |
| GET / | 当前个人记录、字段目录、模型策略与未接入能力 |
| POST / | 新建，expectedRevision=0、requestId、source；同一requestId与相同内容幂等，不同内容409 |
| POST /{id}/append | 增加明确关联的来源，expectedRevision、source |
| POST /{id}/extract | 模型字段与解读，expectedRevision、consent={provider,model,confirmed:true} |
| POST /{id}/edit | 人工字段更正，expectedRevision、fields、reason；null清空字段 |
| POST /{id}/ask | expectedRevision；AI解读或人工校对后生成面向原提报人的请求，返回review.id及@预览 |
| POST /{id}/reply | expectedRevision、reviewId、text（1至3000字符）；只收原提报人对当前请求的回复 |
| POST /{id}/confirm | expectedRevision、reviewId、confirmed=true；本人确认请求绑定的已保存版本 |
| POST /{id}/retract | expectedRevision、reason；保留历史，停止修改 |

source接受text、kind（text/manual_transcript/mock_group）、可选attachments、materialConfirmed。示例：

```json
{
  "requestId": "synthetic-msg-001",
  "expectedRevision": 0,
  "source": {
    "kind": "mock_group",
    "text": "二车间3号灌装机漏液，批次B240914，估计二十多箱受影响。"
  }
}
```

结构化字段保存value、origin、sourceId、verification；AI结果必须来自对应来源的逐字片段。人工修改标为human_correction并保留原因。当前只证明来源匹配，不证明字段语义正确，因此不能绕过人工核对。

状态为draft、awaiting_reporter、confirmed_report、retracted；verification固定为reported_not_business_verified，integration固定为not_connected。每次状态变更注册anomaly.report.changed事件（AnomalyReport v1），事件送达消息总线也不等于ERP接收或业务写入成功。

AI原生answer要求fields、insights、questions。insights为1至6条，至少一条understanding，其他类型为risk/suggestion，每条最多600字符、1至3条有效原文引证；questions最多5条，每条300字符。匹配引文只证明来源存在，不能机械证明推理正确。模型失败不补写模板分析。修改后的旧分析标记stale；人工校对后可发起人工确认，但旧AI分析不进入新确认消息。

review保存请求ID、baseRevision、recipientSubjectId、问题及消息快照；reply/confirm需同时匹配当前版本、请求ID和已认证提报人。客户端不能指定收件人或伪造发送者。回复保存为reporter_reply来源，并留在版本历史。delivery始终为not_connected：本站收到回复不意味着钉钉已发送或收到了消息。旧记录仅在其原个人作用域内绑定原登录主体。

## 钉钉真实接入的下一阶段

标准机器人群聊接收通常要求@机器人；Stream模式不扩大消息读取权限。参考[钉钉接收说明](https://opensource.dingtalk.com/developerpedia/docs/learn/bot/appbot/receive/)与[官方Node SDK](https://github.com/open-dingtalk/dingtalk-stream-sdk-nodejs)。这些链接是接入依据，不代表本项目已联调。

后续需准备：企业机器人应用与凭据、授权群清单、员工账号映射、目标端支持的消息类型、附件下载权限、成员告知与留存规则。第一批只接授权@消息或汇报入口；没有正式全群读取能力时不能承诺无感监听。

开发顺序：

1. 新增经认证的接入适配器与群授权收件箱，消息ID/群ID/企业ID由适配器校验，不能由当前人工入口伪造。将已验证发送者映射为提报人，通过平台人员ID发送真正的@消息；保存平台消息ID、投递状态和请求关联。回调回复必须核对企业、群、发送者及请求，不能用文本中的“@姓名”作为身份凭证。
2. 接入录音下载、格式验证、ASR、分段时间位置及转写校对，验证文字与照片分开提交的关联。
3. 元域智语端发布异常元模型和映射；基于明确键匹配设备、批次和订单，多候选要求人工选择，不按名字猜关系。
4. 智脑在权限范围内读取确认事件与已发布模型，分析影响；草稿和撤回事件不得当作已核实事实。
5. 接入指定下游系统。写操作独立授权，幂等投递、真实回执、更正补偿和失败重试均需验证。
