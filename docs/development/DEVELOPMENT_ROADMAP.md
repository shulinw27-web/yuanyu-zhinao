## 阶段安排：以 Mock 完成开发与验收

| 阶段 | 开发与验证重点 | 模拟输入 | 阶段验收标准 |
| --- | --- | --- | --- |
| 1. 模拟企业与接入项目 | 统一场景选择、材料清单、缺项提示和接入进度；复用现有案例资产 | 企业 A/B 的隔离身份、业务问题、API 文档、需求、字典、制度和样本 | 从空白测试工作区开始；能指出缺什么、为什么需要、下一步做什么；不靠预装已发布模型完成验收 |
| 2. 数据通道与业务对齐 | 接口连接测试、字段预览、认证/分页/过滤/限流/错误处理；跨来源标识、粒度、单位和状态映射 | 本地 HTTP 模拟 ERP/WMS/MES/QMS/OA/OMS 等系统；先选首场景必要的两三个系统 | 请求真正经过连接器与权限校验；样本可核对；冲突、覆盖不完整和失败不会被误报为接入成功 |
| 3. 可用世界模型 | 材料提取、可视化人工修正、对象关系、规则与读取方案、独立回放、版本发布 | 完整与残缺材料、多外键、同名异义、冲突制度、样本事件 | 约定业务问题有可执行读取与计算方案；未知内容进入待确认；人工修正可追溯；发布回执对应当前模型 |
| 4. 双 Agent 业务验收 | 元域智语发布后由智脑读取；关联知识证据、多轮追问、更正、权限及记忆边界 | 合成业务问答、独立答案、第二租户同名编号与不同权限身份 | 每题核对计算、范围、来源、时点和权限；区分事实/推断/建议；未发布草稿不影响线上答案；不声称执行了未授权动作 |
| 5. 持续变化与故障恢复 | 全量/增量模拟、乱序去重、取消/删除、来源延迟、规则修订、接口变更及重启恢复 | 版本化事件序列、固定测试时钟、接口故障与撤权事件 | 数据变化按约定测试时效反映到答案；断链能解释；旧结果不冒充最新；模型变更触发相关回归 |
| 6. 场景复用与受控动作 | 沉淀场景包；更换企业字段和编码；模拟草稿、确认、审批、执行与回执 | 第二家模拟企业、不同映射与业务口径、重复提交、超时及迟到回执 | 列明所需人工配置和代码变更；核心能力可复用；模拟写入需授权且幂等，审批通过不等于执行成功，未知结果先查回执 |

同一阶段可以修复此前已发现的问题，但不能为了通过 Mock 验收而关闭租户隔离、权限、发布校验或生产门禁。测试使用隔离租户、存储和本地模拟端点，不改动用户在用数据。现有沙箱不开放的业务能力，应先设计明确的测试准入，不通过伪装 Demo 身份绕过。

`evaluate:mock-onboarding` 已覆盖材料准备、两家企业的内置 Mock HTTP 读取和故障拒绝；项目按租户/主体/角色分区，源实例每次测试独立创建并关闭。旧 `mock-scenario-service.js` 仍使用固定 `mock_simulation/workspace` 存储键，不能直接作为多租户隔离已完成的依据；本次没有复用它。未完成可信租户作用域改造前，复用旧场景时使用相互隔离的测试实例和存储，不在共享实例上混跑两家企业。

## 场景和材料如何组织

先围绕一个问题完成最小链路，例如“这批原料异常会影响哪些生产批次、库存和订单”。最小场景通过后，逐步加入采购、调拨、门店、退货、财务和责任人；订单履约/授信作为另一组不同业务口径的对照。不是一次生成全企业对象清单。

每个场景包准备以下内容；已有的直接复用，缺少的作为开发项补齐：

- 输入材料：接口文档、需求说明、数据字典、流程/制度、脱敏形态的合成记录；扩展合成异常截图和语音材料，单独验证多模态识别。
- 模拟接口：版本、认证范围、分页/筛选约定、来源与更新时间、覆盖声明；可注入 401/403、限流、超时、漏页、字段变化。
- 业务事件：正常路径和分叉，包括计划未执行、审批无回执、批次合拆、取消、重复到账、待检退货和失效责任指派。
- 扩展变体：多订单、多 SKU 竞争同一库存，重复页、漏页与乱序增量，同名业务编号在两个租户并发出现；这些需要综合场景验证，不能只引用分散单测。
- 验收包：至少十个有明确范围的业务问题、人工核定的独立答案、允许的澄清/拒绝结果、每题的来源和计算依据。
- 复现信息：种子、材料/接口/模型版本、测试时点、身份、事件顺序和运行记录；重置只作用于该测试实例。

业务样本可以生成，但“正确答案”不能由同一次 Agent 回答产生。答案文件不能进入模型输入、知识库或文档检索范围。

## 验证分层：哪些可以 Mock，哪些不能冒充

1. **离线确定性回归**：业务系统和模型响应可使用测试替身，验证契约、编排、计算、权限和失败处理。模型固定输出只证明流程，不证明智能理解。
2. **合成业务集成验证**：使用真实运行的本地后端、数据库、Semantica/WeKnora（按本轮范围选用），业务来源仍为 Mock。缺少服务时记录未执行，不用替身结果冒充该服务联调。
3. **真实模型效果评测**：在模型服务可用且调用范围、费用受控时，用合成材料检验理解、推理、上下文和多模态；记录模型版本、耗时和失败结果。云端不可用不阻塞离线开发，但相应效果验收保持待测。
4. **未来企业接入验收**：届时再核对厂商协议、实际网络、授权、数据质量、负载和业务人员确认。独立于前三层，保留 [生产 Checklist](../operations/PRODUCTION_TODO_CHECKLIST.md) 的未完成状态。

只替换外部依赖，不把场景答案硬编码进页面或 Agent。HTTP 端到端验收必须经过正式入口、可信身份、连接器、映射、模型发布和读取链路；已有单元测试可直调纯函数，但不据此宣称完成端到端验收。

## 必须保留的反例与防自证检查

- 更换企业名称、订单编号、金额、单位和数据排列，答案随业务事实变化；不能只识别固定 Demo 编号。
- 至少留一组未用于开发调试的材料/业务分叉作为留出评测；人工方案与 Agent 自动方案分别报告。
- 缺失主键/外键、矛盾规则和缺少换算依据时要求确认，不猜测；确认修正需保留依据、修订记录和重新校验。
- 同一个对象属于两个租户或两个组织时不可混查；无权、撤权、切换租户后不得复用旧数据或记忆。
- 删除证据、改变发布时间或注入未知字段，检查拒绝/澄清和失效处理，而不是仅检查回答是否流畅。
- 自动生成的读取方案须与独立答案回放；只返回 HTTP 200、通过结构校验或生成图节点均不能算业务通过。

2026-09-17 复现的“材料缺主键，人工补充后仍因原始主键/警告校验失败”已于 2026-09-18 修复：保留原材料，单独记录补缺依据、审阅人和版本，仅解除对应缺主键项；样本、其他冲突和采纳确认继续校验。复杂读取方案生成、多来源归一与持续更新仍需后续专项验收。

## 每阶段如何记录结果

每次保存本轮环境、代码/模型版本、实际执行项、预期与实际、证据、缺陷和未测项。统计从空白工作区到首次数据读取、首次可用模型、首个正确跨系统答案的耗时，以及人工修正次数、代码修改量、正确回答/正确拒绝、更新延迟。先建立本地模拟基线，不把本机耗时承诺成客户接入 SLA。

缺陷修复后跑定向回归和受影响链路；阶段完成需重跑该场景的完整链路并更新 [当前状态](../overview/PROJECT_STATUS.md)。Mock 通过只登记模拟验收，不关闭真实接入或上线项。真实企业环境到位后，按 [开发准备事项](DEVELOPMENT_READINESS.md) 接入，不要求重建整个产品流程。

## 每次迭代的验证

按改动范围选择检查。仅文档调整运行文档检查；业务实现修改运行专项与质量回归；前端变化增加对应构建和界面验证。以下是现有命令，不表示本次均已执行。

```powershell
npm run docs:check
npm run quality
npm run build
npm run build:desktop
npm run build:mobile
```

现有离线案例入口为 `npm run test:dual-agent-mock`、`npm run test:supply-chain-fixture` 和 `npm run test:semantic-workbench-fixture`；它们不等于完整 UI/双 Agent/真实模型联调。`evaluate:dual-agent-weknora` 等集成脚本可能访问外部模型，执行前检查配置、输入范围和调用成本，不作为无外部依赖的默认回归。

涉及 Python 语义服务时还需运行其专项测试；涉及发布时还需迁移校验和目标环境验收，见 [开发指南](GETTING_STARTED.md) 与 [部署回滚手册](../operations/DEPLOYMENT_ROLLBACK_RUNBOOK.md)。测试数量以该次命令输出为准，不把旧基线数量写成当前值。
