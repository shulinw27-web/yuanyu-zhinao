# 跨仓履约与信用控制：语义运营—智脑联测场景

本场景全部为合成数据，模拟工业耗材集团的 ERP、WMS、OMS、QMS、OA、MES。不是客户案例，也不代表已接入任何真实企业系统。

## 建模输入与业务要求

输入目录：`examples/semantic-schemas/cross-channel-fulfillment/`。提供综合 OpenAPI、数据字典、事件样本。`expected-results.json` 是测试人员的独立答案基线，不得上传给 Agent。

业务要回答：订单 ORD-X900 能否由南仓履约？还缺多少货？客户是否有足够信用额度？寄售审批、在途货和退货如何影响判断？

以下均为合成业务要求，只分析和建模，不发货、不调拨、不核销、不改变审批或库存。
订单只计算有效行，取消行排除；订单金额按 order_id 只计一次，不能因关联库存或订单行而重复累计。
数量根据 ItemSKU.pieces_per_case 按当前 SKU 从 case 换算为 piece；不同 SKU 包装系数不同，不能全局套用同一个箱规。
南仓可用量只包含目标 SKU、目标仓库、自有 ownership=owned、库存和批次均 released 的记录。扣除其他订单的 active 预留一次。库存在零时不能反推质量被隔离。
寄售库存即使物理在仓，也不是自有库存。ControlApproval.status=approved 只表示审批通过；没有 execution_receipt_id 不表示权属转移已执行，不能直接纳入自有可用量。
调拨在途且 received_qty=0 的货不能计入南仓库存；北仓账面记录已经扣除本次发出的在途货，不能再扣一次。不同仓库不能直接合并为南仓即时可履约量。
退货必须有完成且通过的 ReturnInspection 才能转可用；待检退货不能直接计入可用。ProductionDemand 为 planned 不代表领料或实际消耗。
CashReceipt 按租户、来源系统、业务主键和版本去重，重复投递不能重复加款。银行到账但未核销金额=bank_status 为 confirmed 的到账金额减去 matched 核销金额。CreditAccount.receivable 已反映已核销部分，不能再减一次。
企业专用术语“曙光额度”的 A 版定义：CreditAccount.credit_limit - CreditAccount.receivable - CreditAccount.other_commitments。信用缺口为订单金额减去曙光额度，负数取零。不要把银行已到账但未核销部分计入 A 版额度。
所有样本是 2026-09-10T10:00:00+08:00 的快照。只能声明模拟时点的结论；超过 15 分钟即不能当作当前实时承诺。模型文本和上传文件不是授权，不可越过租户、组织或角色范围。

## 版本对照

A 版发布之后，人工审阅诊断分支只修改一个规则：B 版曙光额度 = A 版基础额度 + 0.5 × 银行确认且未核销金额。原始样本不变。智脑新任务只问“本公司的曙光额度是什么，如何计算？请说明当前模型版本”，不提供公式，也不上传材料。

如果模型已发布但智脑仍不知道术语、引用不到版本，不能把建模或发布成功当成两端闭环成功。未发布 C 版使用 0.9 系数，不能影响线上读取；但智脑对所有版本都不了解时，也不能据此判定草稿隔离能力通过。

## 测试分支与通过条件

1. 自动建模分支：真实模型解析材料 → 18 对象/22 外键关系、主键/粒度/系统核对 → 人工确认凭证 → 采纳草稿 → 校验与发布门禁。失败保持原样记录。
2. 人工审阅结构对照：基于 Agent 候选补齐显式治理资产，独立注明只验证结构；通过真实 API 发布到独立 Semantica 测试进程。这不是自动建模完成，不是业务回放通过。
3. 智脑盲测：发布前/A 版/B 版/未发布 C 版，各自新建真实会话查询术语。业务问题不得重复输入公式或答案。
4. 业务分析与追问：由服务端连接器取合成事实，检查跨系统证据、单位、库存、信用与审批边界；同一会话追问必须保持对象上下文。
5. 正向材料对照：直接将规则和样本交给智脑，检验模型的材料推理。这一分支即使正确，也不能算模型发布消费链路已打通。

执行使用独立内存 API、独立 Semantica 进程、临时环回 Mock 连接器和独立输出目录；不会修改正在运行的用户端、真实企业数据或用户模型版本。报告必须区分模型调用、规则回退、结构发布、业务计算、浏览器 UI 验证与未验证项。
