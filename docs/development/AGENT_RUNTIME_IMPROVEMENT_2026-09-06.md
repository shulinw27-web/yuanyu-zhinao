# Agent 执行闭环改进记录

日期：2026-09-06。范围：业务智脑的只读执行、精确业务查询、长期目标选择、定时编排与测试口径。没有改动企业生产连接配置，没有部署或训练新模型。

## 第一批：执行状态与编排闭环

| 原有问题 | 本轮处理 | 可以观察到的变化 |
|---|---|---|
| 工具并行执行后，计划仍显示等待执行 | 引入只读执行循环，将工具结果核验回写计划、任务、运行记录和证据轨迹 | 每步显示成功、失败、拒绝、证据不足或隔离；部分失败不会标成全部完成 |
| 模型仅在工具运行后总结 | 多领域任务允许模型依据已取得的观测选择下一项只读工具 | 记录选择来源、执行顺序和已观测步骤数；非法输出或端点失败则按授权计划回退 |
| 工具返回或抛错没有独立完成判定 | 校验摘要、证据引用结构和返回内容安全；错误不透传原文 | 失败时阻止生成可执行提案，降低答复置信级别，保留可用的部分分析 |
| 状态查询拼接固定监控数据 | 移除固定的“1 个 P0 风险、ERP 延迟 6 分钟、7×24 在线”前缀 | 答复不再由该分支添加未经本轮读取确认的状态 |
| 长期记忆只看最近三项，同领域默认用最近一个 | 在当前身份及角色可见的全部有效目标中匹配完整业务编号或记忆 ID；多候选要求选择 | 较早任务可被找回；同领域不同任务不再自动混用；未匹配编号不回退到另一个目标 |
| 定时编排把任何正常返回都当成功 | 核验 Agent 的授权、生命周期、只读核验状态和证据轨迹；待确认还必须有真实确认凭据 | 拒绝、澄清和不完整分析会阻断后续依赖，不再虚构提案已待确认 |
| 模型 HTTP 请求没有截止时间 | 三类模型 HTTP 请求均增加超时，涵盖响应体读取 | 默认 30 秒；下一步选择最多 10 秒；超时回退并释放并发配额 |
| 稳定性指标容易被误读为后端内存 | 区分客户端内存与未测量的服务器内存，增加请求超时和明细数量上限 | 报告使用 `http-soak.v2`，旧测试报告补充勘误 |

## 第一批实现边界

这轮不是通用自主 Agent 重写。业务领域仍由原有规则识别；循环只使用三个已实现的只读分析工具：生产质量、市场影响、内务核验。模型最多做两次顺序选择，每个工具最多执行一次，不重试失败工具、不扩展领域、不执行写入。

工具完成必须满足：已有授权允许调用、真实调用返回非空摘要和有效证据引用结构、内容通过现有安全检查。这里验证的是调用和引用结构，不等于验证了结论真实性、数据时效性或用户完整业务目标，因此返回 `verification.verifiesBusinessGoal=false`。当前工具仍有 Demo 数据和固定业务场景，不能当作任意企业查询引擎。

单领域任务不额外调用规划模型。`mock` 模式按确定性顺序执行，明确不代表模型自主规划。模型接口继续使用现有白名单、配额、脱敏与输出约束。只读步骤检查调用授权，但没有在本轮新增跨进程的实时撤权机制；完整权限时效验收仍需企业身份环境。

只读执行完成与业务写入完成分开记录。新增运行状态 `analysis_completed` / `analysis_incomplete`；实际写执行记录仍为 `execution`，不会因只读核验成功而被填充。既有待确认动作仍须原用户确认及原有业务权限校验。

## 第二批：按业务编号精确查询

第二批将三个只读工具改为支持服务端校验后的 `businessIds` 参数。模型仍只选择工具顺序，不能自行增加编号、角色、组织或 SQL。单次最多 10 个编号，每个不超过 100 个字符。没有编号时保留既有概览查询。

已经完成：

- 编号按完整标识匹配、统一大写并去重；`ORD-100` 不会命中 `ORD-1000`。RC、RM、PB、ORD、SUP 等已知前缀可辅助领域路由，但不赋予数据权限。
- 系统检索有编号时只保留匹配记录，不再补热门订单和默认告警。连接器即使忽略请求条件，返回记录仍须通过服务端编号过滤。门店编号只补充 OMS 数据源，不扩大到 QMS。
- 风险工具查询指定风险，而不是总选最高优先级风险；返回已有记录的状态。例如 `RC-2026-0041` 返回“处理中”，不再被描述为另一个 P0 风险“待确认”。
- 当前消息明确指定编号时，覆盖历史查询编号；自定义编号可承接已经选定的历史任务领域，但不会把旧编号一并送往连接器。
- 分别记录已匹配、部分匹配、未匹配或不可见。部分匹配不能完成整项查询；未匹配不能被解释成“对象不存在”，也不调用摘要模型补造事实。
- 模型回答若出现证据之外的业务编号，丢弃该回答并返回已核验记录。同一证据经过检索和工具两条路径返回时去重，避免重复计数。
- 企业连接器返回空结果时，不重新启用默认风险、供应商和语义节点来补答案。禁用 Mock 后，同步演示读取器也不再返回模拟事实。
- 带编号的受支持业务写入意图暂时返回“只读核验完成、对象写入尚不支持”，不创建默认场景草稿，也不把用户的写入目标标成完成。

需要注意：演示语义图缺少组织级归属，当前不作为精确业务查询的事实凭据。其独立查询已增加编号过滤和关系端点约束，但接回智脑的精确查询前，仍需组织/租户范围、来源标识和版本有效性校验。风险记录保留已有角色和组织过滤；企业连接器仍需在真实环境验证租户、主体及行字段权限，不能把本轮测试视为完整生产权限验收。

当前没有实现历史时点、时间区间或最新版本查询。对已识别的日期、昨天/最近/最新等时间条件，带编号查询会先澄清，不能拿现有记录代替历史结果。编号匹配只证明记录与目标关联，不证明所有分析结论真实，也不代表用户整个业务目标已经完成。

## 第三批：2026-09-07 持续改进与回归

本节记录第三批状态；最新增量见第四批。各批次的限制与测试结论以对应批次为准。

### 1. 查询计划、事件时间和来源版本

新增 `agent-query-plan.v1`。编号仍由服务器提取，不接受模型生成的 SQL、身份或组织参数。支持明确版本号、单日、连续日期区间、今天/昨天/前天及近 1～366 天的事件记录；日期按 `Asia/Shanghai` 转换为含起点、不含终点的 UTC 区间。连接器收到结构化条件后，返回数据还会再次经过编号、日期和版本筛选。

这里筛选的是 `occurredAt`，不是某日的对象状态快照。“昨天这张订单是什么状态”“最新版本”“截至某日”等请求仍需澄清，不能用事件发生时间冒充有效时间。缺少日期或版本的记录不能补入带该条件的结果，默认风险和供应商数据也不能补齐历史查询。

同一来源、同一对象、同一版本若出现不同内容，保留冲突标识，停止模型结论和写入，整项查询不会显示完成。不同系统、不同版本的记录可以并存；本次没有实现自动跨来源事实裁决。

### 2. 绑定目标的质量调查草稿

Demo 支持对单个可见、未关闭的 `RC` 报警生成质量调查草稿。确认内容显示具体编号；服务端保存目标编号、来源及状态摘要哈希。本人确认后，再从风险库读取对象并核对权限与哈希。状态变化、权限丢失、错误确认凭据或重复执行都不能创建草稿。

该动作只生成等待审批的调查工作项，不确认报警、不冻结批次、不创建 ERP 订单。工具不接收客户端替换后的目标参数。采购申请、市场处置等其他指定对象写入仍不开放，避免套用默认案例；需要分别补齐其业务字段、权威对象绑定及审批契约。跨服务原子快照与写入事务没有在本轮实现，因此不能直接把 Demo 的版本复核用作生产强一致保证。

另外补上自然语言边界：“不要创建”“如何创建”“能否创建”不产生业务确认按钮。

### 3. 语义对象、权限与来源

- 供应商 `Supplier`、采购订单 `PurchaseOrder` 使用独立类型；自定义对象默认以自身编码建模，不再默认归为人员。
- 两个模型编辑界面支持选择“独立类型”。这只是类型定义，不增加业务数据访问权或可执行工具。
- 草稿保存拒绝悬空关系、重复关系和无效基数，不再静默删除错误关系后显示保存成功。
- 元模型公开 `semantic-record.v1` 数据契约。生产连接器记录必须包含稳定编号、租户、组织、来源版本、发生时间和分级；缺字段默认拒绝。显式跨租户或组织越权记录即使在非生产环境也被过滤。
- 语义演示图按 Demo 租户、角色和组织过滤，节点携带来源版本标识。它仍是演示投影，不作为精确查询的当前业务事实。
- 语义决策改为按租户和用户持久化，再按角色返回。其他租户或用户不能看到当前用户的决策记录。

生产连接器仍是受信任的数据提供方，本轮元数据校验不证明供应商返回内容真实，也不代替企业行级、字段级权限联调。现有映射演练仍使用受控 Mock 样本；真实数据映射对账尚未完成。

### 4. 结构化记忆与长会话

固定长期目标保存完整安全文本，最多 8000 字符；摘要只用于列表展示。同前缀、不同业务编号的目标不再被错误合并，超过上限会拒绝而不是截断保存。长期目标仍最多 24 项、保留 90 天，且必须由用户固定；没有进行参数训练或自动收集个人信息。

会话增加四类索引：目标、证据引用、决策状态、产物回执。证据只保留来源、编号、版本等引用信息，一天后过期，使用时必须重新查询；模型声称“文件已经生成”不能创建产物记录。索引不继承授权，不作为新一轮写入许可。

权限变化后，获取会话、获取上下文、固定目标和归档任务的响应都隐藏旧权限下的摘要、结构化索引和模型消息。50 轮压缩测试包含三个目标和两次目标更正，确认“继续”不会把旧编号重新混入当前查询。

这仍是结构化索引加摘录压缩，不是经过真实模型验证的语义摘要，也不是无限记忆。50 轮测试验证存储和路由，不等同于大模型连续对话质量验收。

### 5. 运营规划与答复可信度

元域智语规划器复用模型网关的 10 秒超时；测试不再通过 `NODE_ENV=test` 跳过模型调用。HTTP 协议测试验证：模型把“检查状态”建议成“发布模型”时，实际意图和目标仍保留服务器的只读请求，不能扩展系统范围。

答复治理不再因“两条以上引用”直接给出高可信度。当前输出明确说明检查范围是证据引用，不是答案正确率。业务智脑的三个只读工具循环与运营端的单命令审核流程仍是不同实现，没有宣称两端已统一为通用自主规划器。

### 6. 固定评测集与运行方法

数据集：[固定案例](../../examples/agent-evaluation/cases.json)。执行器：[能力评测脚本](../../scripts/evaluate-agent-capabilities.mjs)。只使用合成 Demo 数据及进程内存，不操作现有 SQLite 工作区。

```powershell
# 不调用模型，只检查案例是否产生越界动作、错误编号或错误状态
node scripts/evaluate-agent-capabilities.mjs --mock-contract-only

# 启动本地推理服务，并设置精确模型名、端点和白名单后执行
node scripts/evaluate-agent-capabilities.mjs
```

真实模式首先核对 `/v1/models` 的精确模型名。模型未在线时结果为 `blocked`，案例不会执行；实际调用后若进入降级回答，也不能算模型推理通过。自动断言通过后，仍需按照每条 `rubric` 人工评审回答。图像理解、真实长对话和桌面文件落地列为独立人工验收项。
