# 复杂业务建模与智脑工作台联测

> 本文保留修复前失败证据，不代表当前能力状态。后续实现、回归结果与仍有限制见 [闭环修复报告](SEMANTIC_WORKBENCH_LOOP_REPAIR.md)。

日期：2026-09-10。结论：**候选结构与样本映射通过，但“语义运营建模后，智脑自动理解新业务”的通用闭环未通过。**

这次验证的是两个端实际使用的 HTTP API、真实方舟推理及独立 Semantica 服务，不是仅运行内部模拟函数；没有操作浏览器或 Electron 界面，因此不宣称完成 UI 验收。原业务服务和用户模型版本未修改。

## 1. 场景与独立基线

详见 [场景及需求](SEMANTIC_WORKBENCH_COMPLEX_SCENARIO.md)。工业耗材跨仓履约涉及 ERP/WMS/OMS/QMS/OA/MES，共 18 类对象、22 条字段级外键关系、34 条唯一记录和 1 次重复到账投递。包含不同商品箱规、取消订单行、其他订单预留、寄售货权、跨仓在途、退货待检、信用与到账核销。

以下是测试人员独立计算的合成时点答案，不是智脑本次返回的结果，也没有输入盲测提示词：

| 项目 | 正确基线 |
| --- | --- |
| ORD-X900 金额 | 9,000 CNY，按订单计一次 |
| 有效需求 | 180 件；另一取消行排除 |
| 南仓自有可用量 | 40 件：6 箱 × 10 − 其他订单预留 20 |
| 缺货量 | 140 件 |
| 银行确认但未核销金额 | 7,000 CNY；到账去重，已匹配部分不重复计算 |
| A 版曙光额度 / 信用缺口 | 4,000 / 5,000 CNY |
| B 版曙光额度 / 信用缺口 | 7,500 / 1,500 CNY |
| 寄售审批、待检退货 | 审批不等于货权转移；待检不等于可用 |

独立测试 `backend/test/semantic-workbench-fixture.test.js` 校验材料一致性、全部外键、单位/库存计算、信用去重及因果边界。它只校验测试基线，不是产品业务计算器。

## 2. 测试如何避免“假闭环”

- 语义 Agent 收到 API、字典、样本及需求；智脑盲测不收到这些材料、公式或答案。
- 自动候选采纳走真实的一次性确认与执行入口，不直接改存储。
- 自动链路失败后，单列“人工审阅结构对照”：使用实际候选的 18 对象/22 关系，补齐明确的治理元数据，发布 A/B 两个结构版本到隔离 Semantica。这不是自动业务验收通过，也没有降低原模型的发布门禁。
- 人工结构分支未绑定可执行业务判断，明确 `requireCaseReplay=false`、规则不可执行、权限默认拒绝；只用于证明“已经存在可查询的发布定义”是否被智脑读取。不能据此声称新业务对象已经得到访问或执行授权。
- A/B 原始事实完全相同，仅信用口径及其版本说明变化。未发布 C 版改变系数，不应改变智脑读到的 B 版。
- 材料直接推理另设 P 系列正向对照，不计入发布消费链路通过率。

## 3. 已核实的链路结果

| 测试 | 实际结果 | 判定 |
| --- | --- | --- |
| S1 新场景建模 | 18/18 对象、主键、来源、粒度正确；22/22 字段级外键关系正确 | 结构通过 |
| S1 上传样本映射 | 34 条样本通过，跳过 1 条重复到账；需求原文保留为待评审资产 | 有界样本通过，不是业务计算通过 |
| S2–S5 确认、采纳及 API 校验 | 采纳与校验成功；候选合并既有模型后共有 28 类对象、32 条关系 | 本地结构通过 |
| S6 独立服务构建 | HTTP 422：Semantica 上限 20 类对象，API 上限 40 类 | 失败 |
| S7 自动发布 | HTTP 409，`PUBLICATION_REPLAY_REQUIRED` | 门禁正确阻断；业务闭环未完成 |
| A/B 人工结构发布对照 | 两版均得到真实独立服务的版本与指纹回执 | 结构发布通过，不是自动建模完成 |
| B0 发布前问曙光额度 | 回答没有权威定义，未编造公式 | 边界合理 |
| B1/B4 发布 A/B 后同样提问 | 仍称没有定义或模型版本资料，未引用发布定义 | 发布消费失败 |
| B1a 去掉“版本”字样问业务 | 仅拿到 OMS 3 条相关记录，不能计算库存、箱规、信用；实际调用 OMS/QMS | 跨系统规划与关联查询失败 |
| B2 请求说明模型版本 | 被要求“提供明确来源版本号”，未读取业务数据 | 版本语义误判 |
| B3 同一会话追问 | 记住 ORD-X900 及订单行，调用 5 个连接器；仍只保留直接匹配的 3 条记录，无法算缺口 | 对象上下文部分通过，业务闭环失败 |
| B5 未发布 C 版 | 未暴露 C 版公式，但本来就读不到 A/B | 无法据此判定版本隔离通过 |
| N1/N2 更换身份读取任务 | 智脑会话及语义任务均返回 404 | 本次任务隔离通过，不代表完整 IAM 验收 |
| P1 完整样本直接推理 | 两轮均约 30 秒返回 `understanding_failed`；附件解析状态非截断 | 此输入下理解失败，不能仅凭状态定位为模型本身或容量问题 |
| P2 精简 JSON 直接推理 | 约 25.6 秒；180/40/140 件及 4,000/5,000/7,000 CNY 全部正确 | 六项计算通过，仅为直接材料推理 |
| P3 精简材料同会话追问 | 约 8.8 秒；准确引用 AP-X1 空执行回执、LOT-X7 released 与零库存 | 两项因果边界及材料上下文通过 |

B3 没有把审批通过说成货权转移已执行，也未生成业务执行命令；但引用了与该订单履约无直接证据关联的采购流程提示，说明旧知识路由仍会影响回复。

P2 保留相同的业务字段和重复到账，删除重复的 statement 文本及单租户/单版本信封，输入由 16,819 字节缩为 5,407 字节。没有加入答案或派生计算结果。它证明当前方舟模型在获取规则和完整业务事实后能够完成本场景推理；不能证明业务侧已经自动获得这些规则和事实，也不能证明简化后的载体具备生产来源治理。

测试脚本曾把精简材料做成 TXT，当前产品正确按支持格式清单拒绝；这属于测试输入选择问题，不计为产品逻辑缺陷。已将脚本改成支持的 JSON 并独立复测。第二轮 P3 只凭前文规则的回答不作为实例推理验收，P2/P3 通过结论取第三个证据目录中成功接收 JSON 后的结果。

## 4. 问题清单与修复顺序

本轮新增的是评测资产、测试脚本及文档，**下列产品问题尚未修复**。

| 编号 | 优先级 | 问题与依据 | 修复验收条件 |
| --- | --- | --- | --- |
| SL-01 | P0 | 通用已发布模型未进入智脑对话/业务上下文；A/B 盲测均失败。`semantic-context-service.js` 仍查固定 Demo 图 | 按租户与身份读取允许访问的发布定义；新会话准确解释自定义术语并引用版本，不能靠重复上传材料 |
| SL-02 | P0 | 路由仍依赖预设业务域；跨系统首问未规划完整来源，固定编号过滤不能做关系展开 | 从订单沿显式 FK 查询客户、商品、库存、预留及账户；每跳重新授权、限量、保留来源，不自动扩大权限 |
| SL-03 | P0 | 规则是不可执行的待评审文本，信用指标未形成受控计算和案例回放；不具备新业务自动计算闭环 | 人工审阅规则后绑定受限计算能力；单位、去重、粒度、状态都可回放；禁止直接执行模型生成代码 |
| SL-04 | P1 | API 40 对象与独立服务 20 对象上限不同，28 对象草稿本地通过但部署失败 | 契约统一，边界测试覆盖 20/21/40/41；采纳前提示部署能力限制，不能静默截断 |
| SL-05 | P1 | “说明模型版本”被 `agent-query-plan-service.js` 当成来源版本筛选 | 分开模型版本、业务记录版本、事件时间、历史快照；同义问法不应阻断普通只读查询 |
| SL-06 | P1 | 新通用模型默认合并现有 OA 对象，共享固定 `oa-governance` 槽；业务回放绑定为空却要求回放 | 明确新建/合并及模型命名空间；展示业务回放缺失内容，不能移除门禁来假装完成 |
| SL-07 | P1 | 大材料对话存在理解失败；规则识别也主要是关键词分类，不能以 coverage.complete 证明业务理解 | 记录材料预算、完整性、模型失败原因；以同事实不同载体和数值断言验收，不用成功的结构抽取替代推理 |
| SL-08 | P1 | 业务回答缺少通用模型版本及关系查询链的可追溯证据 | 回答附模型版本/指纹、记录版本、时点与计算依据；模型发布后旧会话的版本策略明确，C 草稿不得生效 |

注意：项目并非“两个端完全没有连接”。`domain-analysis-service.js` 已有 `getPublishedDecisionContext('quality_disposition')`，支持固定质量判断场景的已发布配置。缺的是任意新业务模型到自然语言路由、受控关系查询和计算的通用连接。

## 5. 目标验收闭环

运营端建模并人工审阅 → 数据契约/权限绑定 → 受控业务案例回放 → 版本化发布 → 智脑按身份加载发布模型 → 沿关系查询授权事实 → 执行已注册只读计算 → 带证据和版本回答。

这不是训练一次大模型就自动获得企业知识。模型定义、源数据、权限和计算器要在运行时连接起来。B 版只改变信用规则，智脑回答应从 4,000 变为 7,500；在此之前不能声称“世界模型已驱动智脑”。

## 6. 复现与证据

在项目目录配置好项目外的方舟配置后执行：

```powershell
$env:PATH = 'D:\wsl\workspace\node;' + $env:PATH
npm run test:semantic-workbench-fixture
npm run evaluate:semantic-workbench
```

需要已有 `.venv-semantica/Scripts/python.exe`。脚本自动分配环回端口、启动自己拥有的 API/Python 进程，以内存存储隔离语义版本和会话，结束时只停止自己启动的进程。Mock 返回事实，不返回规则或答案；实际方舟调用会消耗已配置账户额度。

原始证据按运行时间放在 `output/semantic-workbench-loop/`：首轮 `2026-09-10T00-09-59-636Z`，增加对照后的第二轮 `2026-09-10T00-13-10-275Z`。各用例 JSON 保留实际 HTTP 返回、时延、连接器请求；独立发布回执另外保存。时间目录使用 UTC。
